# 改善代码库架构

找出架构带来的阻力，提出**模块加深机会**：将浅模块转为深模块的重构。目标是可测试性和便于 AI 导航。

本命令*以项目领域模型为依据*，并建立在共享设计词汇之上：

- 用 "codebase-design" 调用 Skill 工具，获取架构词汇（**模块**、**接口**、**深度**、**seam**、**适配器**、**杠杆效应**、**局部性**）及其原则（删除检验、“接口就是测试面”、“一个适配器 = 假想 seam，两个 = 真实 seam”）。每项建议都严格使用这些术语，不要偏移为 "component"、"service"、"API" 或 "boundary"。
- `GLOSSARY.md` 中的领域语言为合适的 seam 命名；`docs/adr/` 中的 ADR 记录了本命令不应重新争论的决策。

<a id="process"></a>

## 流程

<a id="1-explore"></a>

### 1. 探索

**扫描前先界定范围：YAGNI。** 加深模块的回报，是让未来修改它更容易，因此应当更重视代码库中最近发生变化的部分。先决定*去哪里看*，再看：

- 如果用户指定方向（模块、子系统、痛点），就采用它，跳过下面的推断。
- 否则，沿提交历史回溯足够长的一段（`git log --oneline`），找出代码库热点，即反复出现的文件和区域，优先关注这些路径。如果改动分散，没有明确热点，就扩大范围。

先阅读项目领域术语表（`GLOSSARY.md`）和所涉及区域的 ADR。

然后启动一个子 agent 遍历代码库。不要遵循僵化的启发式规则；自然探索，记录你遇到的阻力：

- 理解一个概念，在哪里需要在许多小模块之间来回跳转？
- 哪些模块是**浅的**，接口几乎与实现一样复杂？
- 哪里仅为可测试性提取了纯函数，但真正的 bug 藏在调用方式中（缺少**局部性**）？
- 哪里紧密耦合的模块跨 seam 泄漏？
- 代码库哪些部分没有测试，或难以通过当前接口测试？

对怀疑为浅模块的对象应用**删除检验**：删除它会集中复杂性，还是仅仅转移复杂性？“是的，会集中”就是你要找的信号。

<a id="2-present-candidates-as-an-html-report"></a>

### 2. 用 HTML 报告呈现候选项

将自包含 HTML 文件写入操作系统临时目录，不让任何内容进入仓库。优先从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 则为 `%TEMP%`），写入 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都有新文件。替用户打开（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告诉用户绝对路径。

报告使用 **CDN 版 Tailwind** 进行布局和样式设计，结构适合用图／流程／时序可靠表达时，使用 **CDN 版 Mermaid**。将 Mermaid 与手工 CSS/SVG 可视化混合使用：关系呈图结构时（调用图、依赖、时序）使用 Mermaid；希望更像编辑设计图示时（体量图、剖面图、折叠动画），使用手工 div/SVG。每个候选项都有**改前／改后可视化**。重视视觉表达。

为每个候选项呈现一张卡片，包含：

- **文件**：涉及哪些文件／模块
- **问题**：当前架构为什么造成阻力
- **解决方案**：用浅显英语说明会改变什么
- **收益**：用局部性与杠杆效应说明，以及测试如何改善
- **改前／改后图示**：并排、定制绘制，展示浅模块及其加深结果
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三者之一，以徽章呈现

报告最后用 **Top recommendation（首要推荐）**章节说明：你会先处理哪个候选项，以及原因。

**领域用语采用 GLOSSARY.md 词汇，架构用语采用 `/codebase-design` 词汇。** 如果 `GLOSSARY.md` 定义了 "Order"，就说“Order 接入模块”，不要说“FooBarHandler”，也不要说“Order 服务”。

**ADR 冲突**：如果候选项与现有 ADR 冲突，只有阻力真实到值得重新审视该 ADR 时才提出。在卡片中明确标记（例如警告框：_“与 ADR-0007 冲突，但值得重新讨论，因为……”_）。不要列出 ADR 所禁止的每一种理论上的重构。

完整 HTML 骨架、图示模式和样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

此时不要提议接口。写完文件后，询问用户：“你想进一步探索哪一个？”

<a id="3-grilling-loop"></a>

### 3. 追问循环

用户选定候选项之后，用 "grilling" 调用 Skill 工具，与用户遍历决策树：约束、依赖、加深后模块的形态、seam 背后放什么、哪些测试保留。

决策明确时，相关写入随即发生；用 "domain-modeling" 调用 Skill 工具，在过程中保持领域模型最新：

- **要用 `GLOSSARY.md` 中没有的概念命名加深后的模块？** 将术语加入 `GLOSSARY.md`。文件不存在时按需创建。
- **对话中精炼了一个模糊术语？** 当场更新 `GLOSSARY.md`。
- **用户基于关键理由拒绝了候选项？** 提议 ADR，措辞为：_“要我把这记录为 ADR，让未来架构审查不再提出同样建议吗？”_ 只有未来探索者确实需要这个理由来避免重复建议时才提议；跳过临时理由（“现在不值得”）和不言自明的理由。
- **希望为加深后的模块探索不同接口方案？** 用 "codebase-design" 调用 Skill 工具，使用其 design-it-twice 并行子 agent 模式。
