一个模糊想法出现了，大到一个 agent 会话容纳不下，周围迷雾重重：从这里通往**目标**的道路尚不可见。寻路是要找到这条路，而非冲向目标。本技能在仓库的 issue 跟踪器上绘制**共享地图**，再逐张处理其中的**决策工单**（解决后产出决策的问题，而非待执行的构建切片），直到路线清晰。

每项工作的目标都不同，命名目标是绘图的第一步，因为它决定每张工单的形态。目标可以是供交接和迭代的规格说明、规划开始前需锁定的决策，或就地进行的变更，比如数据结构迁移。地图不限定领域：工程工作、课程内容，凡符合这种形式的都适用。

<a id="plan-dont-do"></a>

## 规划，而非执行

Wayfinder 默认做**规划**：每张工单解决一个决策；当道路清晰，在有人动手做事之前已没有待决定的内容时，地图就完成了。忍不住想直接动手，通常意味着已到达地图边界，该交接了。某项工作可以在 **Notes** 中覆盖这一默认行为，把执行也纳入地图；没有这种覆盖时，就应产出决策，而非交付物。

<a id="refer-by-name"></a>

## 按名称引用

每张地图和工单都是 issue，因此都有**名称**：它的标题。在所有供人阅读的内容中（过程说明、地图的 Decisions-so-far），都按名称引用，绝不用裸 id、编号或 slug。一堵 `#42, #43, #44` 数字墙难以辨认，名称则一眼可读。id 和 URL 不会消失；用名称包装链接，让它们包含*在名称内*，而不是取代名称。

<a id="the-map"></a>

## 地图

地图是本仓库 issue 跟踪器上带 `wayfinder:map` 标签的单个 issue，是规范产物。工单是地图的子 issue。

地图是**索引**，不是存储库。它列出已作出的决策，指向保存细节的工单；一个决策恰好只存在于一个地方，即其工单，因此地图不复述，只给概要并链接。

**地图、子工单、阻塞关系和前沿查询具体位于哪里，取决于跟踪器。** 你应当已经获得 issue 跟踪器信息；否则，告诉用户运行 `/setup-matt-pocock-skills`。查阅跟踪器文档的 "Wayfinding operations" 章节，了解*这个*仓库如何表达它们。如果没有提供跟踪器，默认使用本地 Markdown 跟踪器。

<a id="the-map-body"></a>

### 地图正文

低分辨率展示整张地图，每个会话加载一次。**不**列出开放工单：它们是通过查询发现的开放子 issue。

```markdown
## Destination

<到达地图终点是什么样：这项工作要通往的规格说明、决策或变更。一两行；每个会话选择工单前都以此定位。>

## Notes

<领域；每个会话应查阅的技能；这项工作的长期偏好>

## Decisions so far

<!-- 索引：每张已关闭工单一行，足以判断相关性，再沿链接深入查看工单保存的细节 -->

- [<closed ticket title>](link): <答案的一行概要>

## Not yet specified

<!-- 参见“Fog of war”：在范围内但尚无法形成工单的迷雾；随前沿推进转化为工单 -->

## Out of scope

<!-- 参见“Out of scope”：判定超出目标的工作；已关闭，永不转化为工单 -->
```

<a id="tickets"></a>

### 工单

每张工单是地图的**子 issue**；跟踪器 issue id 是其身份。正文是一个问题，规模适合一个 100K token 的 agent 会话：

```markdown
## Question

<本工单解决的决策或调查问题>
```

每张工单带 `wayfinder:<type>` 标签，取值为 `research`、`prototype`、`grilling`、`task`（参见[工单类型](#ticket-types)）。地图和工单只带 `wayfinder:` 标签，绝不带 `ready-for-agent` 等分流标签，因为它们产出决策，而非实现工作。

会话**首先**把工单分配给推动地图的开发者来**认领**，然后才能开始任何工作，让并发会话跳过它。受理人*就是*认领标记：开放且未分配的工单就是未认领。

阻塞使用跟踪器的**原生**依赖关系：这很关键，因为它能在跟踪器 UI 中*可视化*呈现前沿，让人无需打开地图就知道哪些可接手。只有缺乏原生阻塞关系的跟踪器才退回正文约定。阻塞某张工单的所有工单都已关闭时，它才**解除阻塞**；**前沿**就是开放、无阻塞、未认领的子工单，即已知领域的边缘。

答案不属于正文，而是在解决时记录（参见[沿地图推进](#work-through-the-map)）。解决工单时产生的资源从 issue 链接出去，不粘贴进来。

<a id="ticket-types"></a>

## 工单类型

每张工单要么是 **HITL**（human in the loop，*与*能代表自己发言的人共同处理），要么是 **AFK**，由 agent 独立推动。HITL 工单只能通过实时交流解决；agent 绝不代替人发言（追问 agent 自问自答就违反了这一点）。

- **研究（Research）**（AFK）：阅读文档、第三方 API 或知识库等本地资源，查明某个决策所等待的事实。由调用 Skill 工具加载 "research" 的子 agent 解决。需要当前工作目录之外的知识时使用。
- **原型（Prototype）**（HITL）：调用 Skill 工具加载 "prototype"，制作低成本、粗糙但具体的产物（提纲、粗稿、桩，或 UI/逻辑代码），供人反应，从而提高讨论保真度。将原型作为资源链接。关键问题是“应当长什么样”或“应当怎样运行”时使用。
- **追问（Grilling）**（HITL）：对话。默认情况。始终调用两次 Skill 工具，分别加载 "grilling" 和 "domain-modeling"。
- **任务（Task）**（HITL 或 AFK）：在作出*决策*前必须完成的手动工作：没有待决定、待做原型或待研究的内容，但不完成它就无法讨论。比如注册服务以便评估 API、开通访问权限、移动数据以看清其形态。这是唯一*做事*而非决策的类型；它因解除决策阻塞而有必要，不是为了交付目标。能独立完成时由 agent 推动（AFK）；否则给人一份精确清单（HITL）。工作完成即解决；答案记录做了什么，以及后续工单依赖的结果事实（凭据位置、新 URL、行数）。

<a id="fog-of-war"></a>

## 战争迷雾

地图*刻意*不完整：不要绘制尚看不清的东西。现有工单之外是**战争迷雾**：隐约知道将面临某些决策和调查，却还无法确定，因为它们依赖未解决的问题。解决一张工单，就会驱散其前方的迷雾，把现在能够明确描述的部分逐一转成新工单，直到通往目标的道路清晰，且不再剩余工单。

地图的 **Not yet specified** 章节记录这种模糊视野：疑似的问题、稍后重访的区域。它是*朝向*目标的未探索前沿：这里的一切都在范围内，只是还不够清晰，无法形成工单。看得多清楚就写多清楚；它也是供协作者了解工作方向的路标。

**是迷雾还是工单？** 判据是现在能否精确说出问题，*不是*现在能否回答。

- 问题已经明确时，**建工单**，即使它被阻塞、暂时无法行动。
- 还不能如此明确表述时，放入 **Not yet specified**。不要预先把迷雾切成工单大小：迷雾比工单更粗，一片迷雾在前沿推进到那里时，可能化成多张工单，也可能一张都没有。

**Not yet specified** 不包括已经决定的内容（Decisions so far）、已存在的活跃工单，以及范围之外的内容（下一节）。

<a id="out-of-scope"></a>

## 范围之外

迷雾只会*朝向*目标聚集。目标确定范围，因此超出目标的工作是**范围之外**：它不是迷雾，也不属于 **Not yet specified**。地图上为它单设 **Out of scope** 章节，记录你有意识地排除出*本次*工作的内容。它因范围而非清晰程度落在这里。

范围外工作永不转化为工单（前沿止于目标），所以只有重画目标时才会回来，而且作为新工作，而非恢复旧工作。

判定超出范围是一种界定范围的行为，不是路线上的一步。如果已存在的工单被发现位于目标之外（绘图时误纳入，或解决问题后才发现），**关闭它**（已关闭工单明确不在前沿上），并在 **Out of scope** 中留一行：概要、超出范围的原因，以及已关闭工单的链接。不要放入 **Decisions so far**，那里记录实际走过的路线；范围边界不是路线上的一步。

<a id="invocation"></a>

## 调用

两种模式。无论哪种，**每个会话绝不解决超过一张工单**，研究工单除外。

<a id="chart-the-map"></a>

### 绘制地图

用户带着粗略想法调用。

1. **命名目标。** 调用两次 Skill 工具，分别加载 "grilling" 和 "domain-modeling"，明确这张地图要通往什么：规格说明、决策或变更。目标确定范围，因此首先确定目标。
2. **绘制前沿。** 再次追问，这次采用**广度优先**：在整个空间展开，不深挖某一条线，找出开放决策和现在可迈出的第一步。**如果没有发现迷雾**（通往目标的路已清晰，整个过程小到一个会话就能完成），就不需要地图。停止，询问用户希望如何继续。
3. **创建地图**（标签 `wayfinder:map`）：填写 Destination 和 Notes，Decisions-so-far 留空，把迷雾勾勒到 **Not yet specified**。
4. **创建现在能明确的工单**，作为地图子 issue，再在**第二遍**连接阻塞边（issue 必须先有 id 才能相互引用）。交叉引用也在第二遍用真实 id 写入，`#<n>` 占位符会自动链接到无关 issue。连接把工单分成前沿与阻塞项；尚不能明确的内容留在迷雾中的 **Not yet specified** 节。
5. **启动研究子 agent。** 为每张新建 `research` 工单启动子 agent，通过 Skill 工具调用 "research" 并行解决，把发现记录在一次性的 `research/<name>` 分支，从工单提供上下文指针。推送分支，但不创建 PR，因为它永不合并。
6. 停止：绘图就是一个会话的工作；不亲手解决任何工单。

<a id="work-through-the-map"></a>

### 沿地图推进

用户提供地图（URL 或编号）来调用。工单是**可选**的：没有指定时，由你而非用户选择下一个决策。

1. 加载**地图**：低分辨率视图，而非每张工单正文。
2. 选择工单。用户指定了就用那张；否则按顺序取第一张前沿工单。**认领它**：做任何工作前，先分配给自己。
3. 按 `wayfinder:<type>` 标签指定的类型解决（参见[工单类型](#ticket-types)）。读取标签，不只读正文，因为正文从不声明类型。**按需放大**：需要时获取关联或已关闭工单全文，通过 Skill 工具调用 `## Notes` 块列出的技能。拿不准时，为 "grilling" 和 "domain-modeling" 分别调用 Skill 工具，共两次。
4. 记录解决结果：以**解决结果评论**发布答案，**关闭** issue，并向地图的 Decisions-so-far **追加上下文指针**。
5. 添加新出现的工单（先创建再连线）；把答案使之能够明确描述的迷雾转成工单，从 **Not yet specified** 清除每片已转化的迷雾，让它只存在于新工单中。如果答案揭示某张工单（本张或其他）超出目标，**判定其超出范围**，而非把它当路线上的问题解决。如果决策使地图其他部分失效，更新或删除那些工单。

用户可能并行处理无阻塞工单，因此应当预期其他会话也在同时编辑跟踪器。
