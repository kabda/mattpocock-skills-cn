针对 `HEAD` 与用户给定固定基准点之间的 diff，开展双维度审查：

- **Standards（标准）**：代码是否符合仓库已记录的编码标准？
- **Spec（规格说明）**：代码是否忠实实现了原始 issue／规格说明？

两个维度由**并行子 agent**运行，避免相互污染上下文，然后由本技能汇总发现。

你应当已经获得 issue 跟踪器信息。如果缺少 `docs/agents/issue-tracker.md`，告诉用户运行 `/setup-matt-pocock-skills`。

<a id="process"></a>

## 流程

<a id="1-pin-the-fixed-point"></a>

### 1. 确定固定基准点

用户指定的内容就是固定基准点（提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。如果没有指定，就询问。

一次确定 diff 命令：`git diff <fixed-point>...HEAD`（三点形式，因此相对于 merge-base 比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定基准点可解析（`git rev-parse <fixed-point>`），且 diff 非空。无效引用或空 diff 应当在这里失败，而不是进入两个并行子 agent 后才失败。

<a id="2-identify-the-spec-source"></a>

### 2. 确认规格说明来源

按以下顺序寻找原始规格说明：

1. 提交信息中的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），通过 `docs/agents/issue-tracker.md` 中的流程获取。
2. 用户通过参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格说明文件。
4. 如果没有找到，询问用户规格说明在哪里。如果用户说没有，**Spec** 子 agent 将跳过，并报告 "no spec available"。

<a id="3-identify-the-standards-sources"></a>

### 3. 确认标准来源

仓库中任何说明代码应当如何编写的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库记录的内容之外，Standards 维度始终包含下方的**坏味道基线**：来自 Fowler《Refactoring》第 3 章的一组固定代码坏味道，即使仓库什么也没记录，仍然适用。它受两条规则约束：

- **仓库规则优先。** 仓库明确记录的标准始终优先；如果它认可某种基线会标记的做法，就不要报告该坏味道。
- **始终属于判断。** 每种坏味道都是带标签的启发式判断（"possible Feature Envy"），绝不是硬性违规。与这里的其他标准一样，跳过工具已经强制执行的内容。

每种坏味道按*是什么* → *如何修复*说明；请对照 diff 判断：

- **Mysterious Name（含混的名称）**：函数、变量或类型的名称无法说明其作用或内容。→ 重命名；如果想不出准确名称，说明设计本身不清楚。
- **Duplicated Code（重复代码）**：相同的逻辑结构出现在变更的多个 hunk 或文件中。→ 提取共享结构，让两处都调用它。
- **Feature Envy（依恋情结）**：某个方法访问另一个对象的数据，比访问自身数据更多。→ 将方法移到它所依恋的数据所在对象上。
- **Data Clumps（数据泥团）**：相同的几个字段或参数总是一起出现（一个类型正呼之欲出）。→ 将它们组合成一个类型，传递该类型。
- **Primitive Obsession（基本类型偏执）**：用基本类型或字符串代替一个值得拥有专用类型的领域概念。→ 为该概念创建自己的小类型。
- **Repeated Switches（重复的条件分支）**：针对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 替换为多态，或由两处共享的一张映射表。
- **Shotgun Surgery（霰弹式修改）**：一次逻辑变更迫使你在 diff 的多个文件中分散修改。→ 将一同变化的内容集中到一个模块。
- **Divergent Change（发散式变化）**：一个文件或模块因多个无关理由被修改。→ 拆分，让每个模块只因一个理由变化。
- **Speculative Generality（夸夸其谈的通用性）**：为规格说明并不需要的需求添加抽象、参数或 hook。→ 删除它；内联回去，直到出现真实需要。
- **Message Chains（消息链）**：调用方不应依赖的长链式导航 `a.b().c().d()`。→ 将整个遍历隐藏在第一个对象的单个方法后。
- **Middle Man（中间人）**：类或函数主要只是向后委托。→ 移除它，直接调用真正的目标。
- **Refused Bequest（拒绝继承的遗产）**：子类或实现者忽略或覆盖了大部分继承内容。→ 放弃继承，使用组合。

<a id="4-spawn-both-sub-agents-in-parallel"></a>

### 4. 并行启动两个子 agent

**Standards 子 agent 的提示词**应当包含：

- 完整的 diff 命令和提交列表。
- 第 3 步找到的标准来源文件列表，**以及完整粘贴的第 3 步坏味道基线**（子 agent 没有其他途径获取）。
- 简报：“按相关文件／hunk 报告：(a) diff 中所有违反已记录标准的地方：引用标准（文件 + 规则）；(b) 发现的任何基线坏味道：给出名称并引用 hunk。区分硬性违规与判断：违反已记录标准可能是硬性违规，但基线坏味道始终属于判断，且仓库明确记录的标准优先于基线。跳过工具强制执行的内容。少于 400 词。”

**Spec 子 agent 的提示词**应当包含：

- diff 命令和提交列表。
- 规格说明路径或已获取的内容。
- 简报：“报告：(a) 规格说明要求但缺失或只完成部分的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似已实现、但实现方式似乎错误的需求。为每项发现引用规格说明中的对应行。少于 400 词。”

如果缺少规格说明，跳过 Spec 子 agent，并在最终报告中注明。

<a id="5-aggregate"></a>

### 5. 汇总

在 `## Standards` 与 `## Spec` 标题下展示两份报告，原样引用或仅做轻微整理。**不要**合并或重新排序发现，因为两个维度是刻意分开的（参见*为什么分为两个维度*）。

最后用一行总结：每个维度的发现总数，以及*各维度内部*最严重的问题（如果存在）。不要在维度之间选出一个总冠军：那正是分开报告要防止的重新排序。

<a id="why-two-axes"></a>

## 为什么分为两个维度

一项变更可能通过一个维度，却在另一个维度失败：

- 代码遵循所有标准，却实现了错误的东西 → **Standards 通过，Spec 失败。**
- 代码完全符合 issue 要求，却违反项目约定 → **Spec 通过，Standards 失败。**

分开报告，可以防止一个维度掩盖另一个维度。
