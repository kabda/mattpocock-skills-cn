# UI 原型

在单一路由上生成**几个截然不同的 UI 变体**，通过底部悬浮栏切换。用户在浏览器里切换变体，选一个（或从各个方案里取喜欢的部分），然后丢弃其余内容。

如果问题涉及逻辑／状态，而不是外观，就选错分支了。请使用 [LOGIC.md](LOGIC.md)。

<a id="when-this-is-the-right-shape"></a>

## 何时适合这种形式

- “这个页面应该是什么样子？”
- “定下来之前，我想看看这个仪表盘的几个方案。”
- “给设置页面试一种不同布局。”
- 任何用户否则会花一天，在脑中三个模糊草图之间做选择的情况。

<a id="two-sub-shapes-strongly-prefer-sub-shape-a"></a>

## 两种子形式：强烈优先选择 A

UI 原型**紧挨着应用其余部分**时更容易判断：真实页头、真实侧栏、真实数据、真实信息密度。孤立的一次性路由像真空：每个变体单独看都不错。只要有合理的现有页面可承载变体，就默认选择子形式 A。只有原型确实没有合适的相邻容身之处时，才选 B。

<a id="sub-shape-a-adjustment-to-an-existing-page-preferred"></a>

### 子形式 A：调整现有页面（首选）

路由已经存在。变体在**同一路由**上呈现，由 `?variant=` URL 查询参数控制。现有数据获取、参数与认证全部保留。只替换渲染。这是默认选择；除非有具体理由，否则就选它。

如果原型对象还没有自己的页面，但*自然应当位于某个页面内部*（仪表盘的新区域、设置页的新卡片、现有流程的新步骤），仍然属于 A。把变体挂载到宿主页面内。

<a id="sub-shape-b-a-new-page-last-resort"></a>

### 子形式 B：新页面（最后手段）

只有原型对象确实没有可容纳它的现有页面时才使用（例如全新的顶层界面，或无法合理嵌入任何位置的流程）。

按项目已有的路由约定创建**一次性路由**。不要发明新的顶层结构。命名要明显表明是原型（例如在路径或文件名中包含 `prototype`）。同样使用 `?variant=` 模式。

确定选择 B 之前，做一次基本核对：真的没有现有页面可以嵌入吗？空白路由会掩盖那些在有内容的页面中会暴露的设计问题。

两种子形式使用相同的底部悬浮栏。

<a id="process"></a>

## 流程

<a id="1-state-the-question-and-pick-n"></a>

### 1. 说明问题并确定 N

默认 **3 个变体**。超过 5 个，就不再是截然不同的方案，而是噪声，因此上限为 5。

在原型所在位置或文件顶部注释中，用一行写下计划：

> “在现有 `/settings` 路由上提供设置页面的三个变体，通过 `?variant=` 切换。”

无论用户是否在场提出异议，这种方式都有效。

<a id="2-generate-radically-different-variants"></a>

### 2. 生成截然不同的变体

起草每个变体。每个都必须符合：

- 页面的目的及其可访问的数据。
- 项目的组件库／样式系统（TailwindCSS、shadcn、MUI、纯 CSS 或其他）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：布局不同、信息层级不同、主要操作方式不同，而不只是颜色不同。三个略微调整的卡片网格不是 UI 原型，只是墙纸。如果两个草案过于相似，就用明确的“不要使用卡片网格”要求重做其中一个。

<a id="3-wire-them-together"></a>

### 3. 将它们连接起来

在路由上创建一个切换组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于 A（现有页面）：保留切换器上方所有现有数据获取逻辑；每个变体只改变渲染子树。

对于 B（新页面）：`/prototype/<name>` 下的一次性路由挂载相同的切换器。

<a id="4-build-the-floating-switcher"></a>

### 4. 构建悬浮切换器

在屏幕底部中央放置一个固定定位的小栏，包含三部分：

- **左箭头**：循环切换到上一个变体。
- **变体标签**：显示当前变体键；如果变体导出了名称，也显示该名称。例如 `B (Sidebar layout)`。
- **右箭头**：循环切换到下一个变体。

行为：

- 点击箭头更新 URL 查询参数（使用框架路由器，例如 Next 的 `router.replace`、React Router 的 `navigate` 等），让变体可共享，且刷新后保持不变。
- 键盘：`←` 和 `→` 方向键也能循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 在视觉上与页面明显区分（例如高对比胶囊形、轻微阴影），让人明确知道它不是被评估设计的一部分。
- 在生产构建中隐藏：通过 `process.env.NODE_ENV !== 'production'` 或等效检查控制，避免意外合并原型时将该栏交付给用户。

将切换器放在单个共享组件中，让两种子形式都能复用。位置遵循项目共享 UI 的存放约定。

<a id="5-hand-it-over"></a>

### 5. 交给用户

展示 URL（以及 `?variant=` 的键）。用户有空时会切换查看。有价值的反馈通常是**“我想要 B 的页头加 C 的侧栏”**，那才是他们真正想要的设计。

<a id="6-capture-the-answer-and-clean-up"></a>

### 6. 留存答案并清理

某个变体胜出后，记录答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 描述的方式留存原型。将胜出方案融入真实代码，其余内容移到一次性分支，不进入 main：

- **子形式 A**：将胜出方案融入现有页面；从 main 移除未选变体与切换器。
- **子形式 B**：将胜出变体提升为真实路由；从 main 移除一次性路由和切换器。

完整变体集合是一手来源，因此进入一次性分支，而不是垃圾桶；变体组件和切换器若留在主分支，会迅速腐化并让下一位读者困惑。

<a id="anti-patterns"></a>

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体对结构有不同主张。
- **变体之间共享过多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就违背目的。每个变体都应当能自由抛弃原有布局。
- **将变体连接到真实修改操作。** 只读原型可以。如果变体需要修改数据，就指向 stub：问题是“应该是什么样子”，不是“后端是否工作”。
- **直接把原型提升到生产环境。** 变体代码是在原型约束下编写的（无测试、最少错误处理）。融入真实代码时，应当正规重写。
