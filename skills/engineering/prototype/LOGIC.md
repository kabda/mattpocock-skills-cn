# 逻辑原型

一个独立、自包含的 HTML 文件（**可共享演示**），让任何人都能通过点击按钮驱动状态模型。当问题涉及**业务逻辑、状态转换或数据结构**时使用：这些东西在纸上看着合理，只有放进真实案例运行时才感觉不对。

因为只有一个文件、无需安装，你可以把它交给非开发者（设计师、PM、领域专家），让他们亲自感受模型。因此它使用他们的语言，而不是代码的语言。

<a id="when-this-is-the-right-shape"></a>

## 何时适合这种形式

- “我不确定这个状态机能否处理先 X 后 Y 的边界情况。”
- “这个数据模型真的能表示这样一种情况吗……”
- “我想在写 API 之前，先感受它应该是什么样。”
- 任何想要**按按钮并观察状态变化**的情况。

如果问题是“它应该是什么样子”，就选错分支了。请使用 [UI.md](UI.md)。

<a id="process"></a>

## 流程

<a id="1-state-the-question"></a>

### 1. 说明问题

写代码之前，写清楚正在为哪个状态模型、哪个问题做原型。用一个段落放在演示顶部（可见的介绍中，而不只是注释里）。回答错误问题的逻辑原型纯属浪费，因此要明确问题，以便之后核对，无论用户现在正在看，还是暂时离开后再回来查看。

<a id="2-isolate-the-logic-in-a-portable-module"></a>

### 2. 将逻辑隔离为可迁移模块

将实际逻辑（回答问题的那部分）放进单个 `<script>` 块，写成一个小型纯模块，以后可以直接提取到真实代码库中。周围的页面是一次性的，这个模块不是。

合适的形式取决于问题：

- **纯 reducer**：`(state, action) => state`。适用于动作是离散事件、状态是单一值的情况。
- **状态机**：明确的状态与转换。当“此刻哪些动作合法”也是问题的一部分时很合适。
- 在普通数据类型上运行的**少量纯函数**。没有隐式当前状态、只有转换时很合适。
- 当逻辑确实拥有持续的内部状态时，使用**方法表面清晰的类或模块**。

选择最适合问题的形式，*不要*选择最容易接到页面上的形式。保持纯粹：不引用 DOM、不使用 `document`、不让按钮处理函数探入内部。页面调用模块，不允许反向流动。这样原型才能在自身生命周期之后继续发挥价值：问题得到回答后，已验证的 reducer／状态机／函数集可以独立提取到真实模块中。

<a id="3-build-the-shareable-html-file"></a>

### 3. 构建可共享 HTML 文件

一个文件，纯 HTML/CSS/JS：不使用框架、打包器或服务器，所有内容内联，让它双击即可打开，也能经受邮件转发。任何人只需打开就能运行。

为非开发者编写。每个标签都使用**领域语言**，而不是代码：按钮和状态读起来像业务，而不是 reducer。用直白的话解释正在发生什么。

从上到下采用清晰层级：

1. **标题和一句话说明**，描述演示让人探索什么（第 1 步的问题）。
2. **当前状态**：展示全部相关状态，用易读面板呈现（带标签的字段，而不是原始 JSON 倾倒），每次点击后重新渲染，让变化可见。如果有助于非开发者理解，就指出刚刚改变了什么。
3. **自由操作按钮**：每个动作一个按钮，始终可用，让任何人都能按任意顺序试探模型。每次点击分派对应动作，并重新渲染状态。
4. **引导演练**：一组**场景**，每个标签页一个。每页先用简短直白的文字描述场景（设置什么情况、应该注意什么），下方按顺序列出该场景**要按的按钮**。每一步都是真实按钮：点击后执行动作，并进入下一步。开始演练时重置到已知初始状态，让场景每次都以相同方式运行。

选择能展示棘手情况的场景，即纸面上难以推理的那些：正常路径、难处理的边界情况、尝试执行本应非法的动作。

保持美观但克制：清晰排版、充足留白、一种强调色。没有动画，没有花招：不要让任何东西与状态和按钮争夺注意力。

<a id="4-hand-it-over"></a>

### 4. 交给用户

将文件交给他们，或替他们打开。他们有空时会点击演练、自由操作；有意思的时刻是他们说“等等，这不应该能发生”或“咦，我以为 X 会不一样”；那是*想法*中的 bug，而这正是全部目的。如果他们想要新动作或新场景，就添加。原型会演进。

<a id="5-capture-the-answer-and-the-prototype"></a>

### 5. 留存答案和原型

原型回答了问题之后，先记录答案，再按 [SKILL](SKILL.md) 描述的方式留存原型。逻辑分支的具体对应关系是：已验证的 reducer／状态机／函数集提取到真实模块中（决策被吸收）；HTML 外壳一同进入保存原型作为一手来源的一次性分支。由于它是一个自包含文件，在那里仍然很容易重新运行。

<a id="anti-patterns"></a>

## 反模式

- **不要添加测试。** 需要测试的原型已经不是原型。
- **不要连接真实数据库。** 除非问题明确涉及持久化，否则使用内存状态。
- **不要泛化。** 不讨论“如果以后想支持 X 呢”。原型只回答一个问题。
- **不要混合逻辑与页面。** 如果纯模块引用 DOM、`document` 或按钮处理函数，就无法独立提取。让页面只是纯模块之上的薄外壳。
- **不要使用框架、打包器或服务器。** 接收者双击一个文件即可；React 应用或开发服务器会破坏“可共享”这一点。
- **不要把 HTML 外壳交付到生产环境。** 页面针对手动点击探索优化。背后的逻辑模块才是值得保留的部分。
