<a id="diagnosing-bugs"></a>

# 诊断 bug

针对棘手 bug 的实践规范。只有明确说明理由时，才能跳过阶段。

探索代码库时，阅读 `CONTEXT.md`（如果存在），建立对相关模块的清晰心智模型，并检查所涉及区域的 ADR。

<a id="redact"></a>

## 脱敏

本技能要求展示命令、输出和捕获的材料。**先隐去每一项秘密信息**：在原位置写 `<REDACTED>`。使用环境变量构建循环，让凭据留在环境里，而不是出现在展示内容中。捕获材料可能携带认证头：只引用提供诊断信号的行。

如果脱敏后的输出不足以诊断 bug，明确说明并询问用户。

<a id="phase-1-build-a-feedback-loop"></a>

## 阶段 1：构建反馈循环

**这就是本技能的核心。** 其他一切都是机械工作。如果你拥有针对该 bug 的**紧凑**通过／失败信号（能够因*这个* bug 变 Red），就能找到原因；二分、假设检验和埋点都只是使用这个信号。如果没有，再怎么盯着代码也救不了你。

在这里投入远高于其他阶段的精力。**积极进取，发挥创造力，拒绝放弃。**

<a id="ways-to-construct-one-in-roughly-this-order"></a>

### 构建方式，大致按以下顺序尝试

1. 在能触及 bug 的任意 seam 上编写**失败测试**：单元、集成、e2e。
2. 针对运行中的开发服务器编写 **Curl / HTTP 脚本**。
3. 使用 fixture 输入执行 **CLI 调用**，将 stdout 与已知正确的快照比较。
4. 用**无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，并对 DOM／控制台／网络进行断言。
5. **重放捕获的 trace。** 将真实网络请求／payload／事件日志保存到磁盘；隔离重放相关代码路径。
6. **一次性测试环境。** 启动系统的最小子集（一个服务、mock 依赖），用一次函数调用执行 bug 所在代码路径。
7. **属性／fuzz 循环。** 如果 bug 是“偶尔输出错误”，运行 1000 个随机输入，寻找失败模式。
8. **二分测试环境。** 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，自动化“在状态 X 启动、检查、重复”，以便使用 `git bisect run`。
9. **差分循环。** 将相同输入分别交给旧版和新版（或两种配置），比较输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人点击，就用 `scripts/hitl-loop.template.sh` 引导*这个人*，让循环仍然结构化。捕获的输出反馈给你。

构建正确的反馈循环，bug 就已经修好了 90%。

<a id="tighten-the-loop"></a>

### 收紧循环

把循环当作产品。有了*一个*循环之后，还要**收紧**它：

- 能更快吗？（缓存准备步骤、跳过无关初始化、缩小测试范围。）
- 信号能更准确吗？（断言具体症状，而不是“没有崩溃”。）
- 能更确定吗？（固定时间、设置 RNG 种子、隔离文件系统、冻结网络。）

一个 30 秒且不稳定的循环，几乎不比没有循环强；一个 2 秒且确定的循环才够紧凑，是调试的超能力。

<a id="non-deterministic-bugs"></a>

### 非确定性 bug

目标不是一次干净的复现，而是**更高的复现率**。将触发动作循环 100 次、并行执行、增加压力、缩小时间窗口、注入 sleep。50% 概率出现的 bug 可以调试，1% 的不行，所以持续提高复现率，直到能够调试。

<a id="when-you-genuinely-cannot-build-a-loop"></a>

### 确实无法构建循环时

停止并明确说明。列出已经尝试的办法。向用户请求：(a) 访问能够复现的环境，(b) 脱敏后的捕获材料（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 添加临时生产环境埋点的许可。**不要**在没有循环的情况下继续提出假设。

<a id="completion-criterion-a-tight-loop-that-goes-red"></a>

### 完成标准：能够变 Red 的紧凑循环

阶段 1 的完成条件是循环既**紧凑**，又**能够变 Red**：你可以指出**一条命令**（脚本路径、测试调用、curl），并且**已经至少运行过一次**（展示脱敏后的调用及输出），还要满足：

- [ ] **能够变 Red**：执行真实 bug 代码路径，并断言**用户的确切症状**，因此能在该 bug 存在时变 Red、修复后变 Green。不能只是“运行时没报错”；它必须能够*捕获这个具体 bug*。
- [ ] **确定性**：每次运行结论相同（不稳定 bug：按上文将复现率固定在较高水平）。
- [ ] **快速**：以秒计，而不是分钟。
- [ ] **agent 可运行**：可以无人值守执行；只有通过 `scripts/hitl-loop.template.sh` 才允许人在循环中参与。

如果发现自己在这条命令尚不存在时就开始读代码、构建理论，**停止：直接跳到假设，正是本技能要防止的失败。** 没有能变 Red 的命令，就没有阶段 2。

<a id="phase-2-reproduce--minimise"></a>

## 阶段 2：复现并最小化

运行循环。观察 bug 出现时它变 Red。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是碰巧相邻的另一种失败。bug 找错，修复也会错。
- [ ] 多次运行能够复现失败（对于非确定性 bug，复现率足够高，能够据此调试）。
- [ ] 已捕获确切症状（错误消息、错误输出、耗时变慢），让后续阶段能验证修复确实解决了它。

<a id="minimise"></a>

### 最小化

一旦变 Red，就将复现缩减为**仍能变 Red 的最小场景**。输入、调用方、配置、数据和步骤，**一次删减一个**；每次删减后重新运行循环，只保留对失败不可或缺的内容。

为什么值得做：最小复现缩小了阶段 3 的假设空间（可疑的变量更少），并成为阶段 5 中干净的回归测试。

当**每个剩余元素都不可或缺**时完成：移除其中任意一个，循环都会变 Green。

复现**并且**最小化之前，不要继续。

<a id="phase-3-hypothesise"></a>

## 阶段 3：提出假设

在测试任何假设之前，先生成**按优先级排序的 3–5 个假设**。只生成一个假设，会锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：说明它所作出的预测。

> 格式：“如果 <X> 是原因，那么 <changing Y> 会让 bug 消失／<changing Z> 会让它更严重。”

如果说不出预测，这个假设就只是感觉：舍弃它，或进一步明确。

**测试前向用户展示排序后的列表。** 用户往往拥有能立即改变排序的领域知识（“我们刚部署了与第 3 项有关的改动”），或知道已经排除过哪些假设。这是低成本、能节省大量时间的检查点。不要因此阻塞；如果用户处于 AFK 状态，就按自己的排序继续。

<a id="phase-4-instrument"></a>

## 阶段 4：埋点

每个探针都必须对应阶段 3 的一项具体预测。**一次只改变一个变量。**

工具优先顺序：

1. 环境支持时，使用**调试器／REPL 检查**。一个断点胜过十条日志。
2. 在能够区分假设的边界添加**定向日志**。
3. 绝不“记录所有内容再 grep”。

**为每条调试日志添加标记**，使用唯一前缀，例如 `[DEBUG-a4f2]`。这样最后只需一次 grep 就能清理。没有标记的日志会留下，有标记的日志会被删除。

**性能分支。** 对性能回归，日志通常不是正确工具。应当先建立基线测量（计时测试环境、`performance.now()`、profiler、查询计划），再二分。先测量，后修复。

<a id="phase-5-fix--regression-test"></a>

## 阶段 5：修复与回归测试

在**修复之前**编写回归测试，但前提是存在**正确的 seam**。

正确的 seam 能让测试按调用点实际发生的方式，执行**真实 bug 模式**。如果唯一可用的 seam 太浅（bug 需要多个调用方，却只有单调用方测试；单元测试无法重现触发 bug 的链路），在这里写回归测试会带来虚假信心。

**如果没有正确的 seam，这本身就是发现。** 记录它。代码库架构正在阻止你通过测试锁定这个 bug。将其标记给下一阶段。

如果存在正确的 seam：

1. 将最小复现转成该 seam 上的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始（未最小化）场景，重新运行阶段 1 的反馈循环。

<a id="phase-6-cleanup"></a>

## 阶段 6：清理

宣布完成之前必须满足：

- [ ] 原始复现不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或已记录缺少 seam）
- [ ] 所有 `[DEBUG-...]` 埋点已移除（用 `grep` 搜索前缀）
- [ ] 一次性原型已删除（或移入明确标注的调试位置）
- [ ] 在提交／PR 信息中说明最终正确的假设，让下一位调试者能够获益
