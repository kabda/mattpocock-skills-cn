# 转为工单

将计划、规格说明或对话拆成一组**工单**：曳光弹式纵向切片，每张声明哪些工单会**阻塞**它。

你应当已经获得 issue 跟踪器和分流标签词汇。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

<a id="process"></a>

## 流程

<a id="1-gather-context"></a>

### 1. 收集上下文

从对话上下文中已有的内容出发。如果用户通过参数传入引用（规格说明路径、issue 编号或 URL），获取并阅读完整正文与评论。

<a id="2-explore-the-codebase-optional"></a>

### 2. 探索代码库（可选）

如果尚未探索代码库，先探索以了解代码当前状态。工单标题和描述应当使用项目领域术语表中的词汇，并遵守所涉及区域的 ADR。

寻找可以预先重构代码、让实现更容易的机会。“先让变更变得容易，再做这个容易的变更。”

<a id="3-draft-vertical-slices"></a>

### 3. 起草纵向切片

将工作拆成**曳光弹**式工单。

<vertical-slice-rules>

- 每个切片贯穿每一层（schema、API、UI、测试），形成狭窄但完整的路径：必须是纵向切片，而不是某一层的横向切片
- 完成的切片可以独立演示或验证
- 每个切片的大小适合一个全新的上下文窗口
- 任何预先重构都应当先完成

</vertical-slice-rules>

为每张工单声明**阻塞关系**：哪些其他工单必须完成，它才能开始。没有阻塞项的工单可以立即开始。

**大范围重构是纵向切片的例外。****大范围重构**指一项机械性变更（重命名列、改变共享符号的类型），其**影响范围**扩散到整个代码库，导致一次编辑同时破坏成千上万个调用点，没有任何纵向切片能以 Green 状态落地。不要硬把它塞进曳光弹切片；应当按 **expand–contract（扩展－收缩）** 排序。先扩展：在旧形式旁边添加新形式，让一切保持正常。然后按影响范围分批迁移调用点（按包、按目录），每批一张工单，均被扩展工单阻塞；旧形式仍然存在，所以各批之间 CI 保持 Green。最后收缩：没有调用方残留后删除旧形式，该工单被所有迁移批次阻塞。如果连各批次也无法独立保持 Green，就保留这个顺序，但让它们共享一个集成分支，并共同阻塞最后一张“集成并验证”工单；只在最后这一步承诺 Green。

<a id="4-quiz-the-user"></a>

### 4. 向用户核对

以编号列表展示建议的拆分。每张工单展示：

- **标题**：简短的描述性名称
- **Blocked by**（阻塞项）：哪些其他工单（如有）必须先完成
- **交付内容**：这张工单实现的端到端行为

询问用户：

- 粒度是否合适？（太粗／太细）
- 阻塞关系是否正确：每张工单是否只依赖真正决定其能否开始的工单？
- 是否需要合并或进一步拆分某些工单？

反复调整，直到用户批准拆分方案。

<a id="5-publish-the-tickets-to-the-configured-tracker"></a>

### 5. 将工单发布到已配置的跟踪器

发布已获批准的工单。**如何**发布取决于 `/setup-matt-pocock-skills` 配置的跟踪器；两种方式的工单相同，只有阻塞关系的形式不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每张工单写一个文件，按依赖顺序从 `01` 开始编号（阻塞项在前）。每个文件的 "Blocked by" 列出其依赖的编号／标题。使用下面的单工单文件模板：每张工单一个文件，绝不合并为单个文件。
- **真正的 issue 跟踪器（GitHub、Linear、…）** → 按依赖顺序发布，每张工单一个 issue，先发布阻塞项，使阻塞边能引用真实标识。平台支持时用原生阻塞关系，否则把阻塞 issue 写进各工单的 “Blocked by”。来源为既有 issue 时，把工单设为它的子 issue（按跟踪器文档操作）。除非另有指示，应用 `ready-for-agent` 分流标签；工单在构造时已可供 agent 接手。

处理**前沿**：所有阻塞项均已完成的工单。对于纯线性链，这意味着从上到下处理。

不要关闭或修改任何父 issue。
