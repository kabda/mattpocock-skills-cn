# ADR 格式

ADR 存放在 `docs/adr/` 中，按顺序编号：`0001-slug.md`、`0002-slug.md` 等。

按需创建 `docs/adr/` 目录：只有需要第一份 ADR 时才创建。

<a id="template"></a>

## 模板

```md
# {决策的简短标题}

{1–3 句话：背景是什么、做了什么决定，以及为什么。}
```

仅此而已。ADR 可以只有一个段落。价值在于记录*已经作出某项决定*以及*原因*，而不是填满各个章节。

<a id="optional-sections"></a>

## 可选章节

只有确实有用时才添加。大多数 ADR 不需要它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：重新审视决策时有用
- **Considered Options**（考虑过的选项）：仅在被否决的替代方案值得记住时使用
- **Consequences**（后果）：仅在需要指出不明显的下游影响时使用

<a id="numbering"></a>

## 编号

扫描 `docs/adr/`，找出已有的最大编号，再加一。

<a id="when-to-offer-an-adr"></a>

## 何时提议 ADR

必须同时满足以下三个条件：

1. **难以撤销**：以后改变主意的成本确实不小
2. **缺少背景时令人困惑**：未来读者看到代码会问“他们到底为什么这样做？”
3. **来自真实的取舍**：确实存在其他方案，而你基于具体理由选择了其中一个

如果决策容易撤销，就跳过：到时候直接撤销即可。如果并不令人困惑，就没人会追问原因。如果没有真正的替代方案，也没有什么需要记录的，无非是“我们做了显而易见的事”。

<a id="what-qualifies"></a>

### 哪些决策符合条件

- **架构形态。** “我们使用 monorepo。”“写模型采用事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 与 Billing 通过领域事件通信，而不是同步 HTTP。”
- **会带来锁定效应的技术选择。** 数据库、消息总线、认证提供方、部署目标。不是每个库都算：只有那些替换起来需要一个季度的选择。
- **边界和范围决策。** “Customer 数据归 Customer 上下文所有；其他上下文只能通过 ID 引用。”明确说不，与明确说是同样有价值。
- **有意偏离显而易见的路径。** “由于 X，我们手写 SQL 而不用 ORM。”任何正常读者会认为应当反过来做的事情。这能防止下一位工程师把有意为之的选择当作问题“修复”。
- **代码中不可见的约束。** “由于合规要求，我们不能使用 AWS。”“由于合作伙伴的 API 契约，响应时间必须低于 200ms。”
- **否决理由不明显的替代方案。** 如果考虑过 GraphQL，却因微妙的原因选择 REST，就记下来；否则六个月后又会有人提议 GraphQL。
