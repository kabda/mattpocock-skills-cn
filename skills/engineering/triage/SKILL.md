<a id="triage"></a>

# 分流

让项目 issue 跟踪器中的 issue 流转经过一个小型分流角色状态机。

如果仓库将外部 pull request 视为请求入口（参见 issue 跟踪器配置），分流也涵盖它们：**PR 就是附带代码的 issue**，使用相同角色、相同状态和相同状态机，下文用“对于 PR”标出少数差异。按跟踪器配置，将单独出现的 `#42` 解析为 issue 或 PR。

分流期间发布到 issue 跟踪器的每条评论或每个 issue，**必须**以以下免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写经得起时间变化的 agent 简报

<a id="roles"></a>

## 角色

两个**类别**角色：

- `bug`：某处出故障
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：规格已完整，可交给 AFK agent
- `ready-for-human`：需要人来实现
- `wontfix`：不会采取行动

对于 PR，同样的状态针对所附代码来解读：`ready-for-agent` 表示已附简报，应由 agent 对 diff 采取下一步行动；`ready-for-human` 表示已可由人合并。

每个经过分流的 issue 应当恰好带一个类别角色和一个状态角色。如果状态角色冲突，先指出问题并询问维护者，再做其他任何事。

这些是规范角色名称，issue 跟踪器实际使用的标签字符串可能不同。你应当已经获得映射；否则，告诉用户运行 `/setup-matt-pocock-skills`。

状态转换：无标签的 issue 通常先进入 `needs-triage`，再转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖；发现看似异常的转换时，先指出并询问，再继续。

<a id="invocation"></a>

## 调用

维护者调用 `/triage`，用自然语言描述需求。理解请求并行动。例如：

- “显示所有需要我关注的事项”
- “看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “有哪些已经可以交给 agent？”

<a id="show-what-needs-attention"></a>

## 展示需要关注的事项

查询 issue 跟踪器，分成三组展示，每组按时间从早到晚排序：

1. **无标签**：从未分流。
2. **`needs-triage`**：正在评估。
3. **`needs-info` 且自上次分流记录后报告者有新活动**：需要重新评估。

当 PR 在范围内时，把外部 PR 也纳入这些分组，每行标记 `[PR]` 或 `[issue]`。发现阶段只显示*外部* PR（跟踪器配置定义何为外部），协作者正在处理的 PR 不属于分流工作。该过滤仅用于发现阶段；明确指定的 PR 无论作者是谁都要分流。

显示数量，并为每项给出一行摘要。让维护者选择。

<a id="triage-a-specific-issue-or-pr"></a>

## 分流指定 issue 或 PR

1. **收集上下文。** 阅读完整 issue 或 PR（正文、评论、标签、作者、日期；PR 还包括 diff）。解析此前的分流记录，避免重复询问已解决的问题。使用项目领域术语表探索代码库，遵守该区域的 ADR。对照代码库做两项检查：(a) **重复性**：按领域概念（不只按请求措辞）搜索所请求行为是否已有实现，报告查过哪些地方。如果找到，就因“已实现”而归为 `wontfix`（步骤 5）。(b) **既往拒绝**：阅读 `.out-of-scope/*.md`，指出与当前请求相似的记录。

2. **提出建议。** 告诉维护者你建议的类别和状态及其理由，并简述与请求相关的代码库情况（包括是否已经实现）。等待指示。

3. **验证说法。** 任何追问之前，先检查说法是否成立。对于 bug，按报告者的步骤复现。对于 PR，确认 diff 实现了它声称的功能：检出并运行相关测试或命令。报告结果：已确认（附代码路径）、失败，或信息不足（这是很强的 `needs-info` 信号）。经过确认的验证能使 agent 简报可靠得多。

4. **追问（如有需要）。** 如果请求需要细化，调用两次 Skill 工具，分别加载 "grilling" 和 "domain-modeling"，逐轮追问使其成形；决策确定时，同步打磨领域术语并更新 `GLOSSARY.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发布 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：采用与 agent 简报相同的结构，但注明无法委派的原因（判断取舍、外部访问、设计决策、手动测试）。
   - `needs-info`：发布分流记录（见下方模板）。
   - 对于 `wontfix`，关闭 issue，评论取决于*原因*：
     - **已实现**：代码库中已存在该变更。指出其位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，而非已经实现的请求）。
     - **被拒绝（bug）**：礼貌说明，然后关闭。
     - **被拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如果已有部分进展，可以发表评论。

<a id="quick-state-override"></a>

## 快速覆盖状态

如果维护者说“把 #42 移到 ready-for-agent”，相信他们，直接应用角色。确认即将执行的操作（角色变更、评论、关闭），然后执行。跳过追问。如果未经追问就转到 `ready-for-agent`，询问是否要编写 agent 简报。

<a id="needs-info-template"></a>

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- 已确定的要点 1
- 已确定的要点 2

**What we still need from you (@reporter):**

- 问题 1
- 问题 2
```

把追问中已解决的所有内容记入 "established so far"，以免成果丢失。问题必须具体且可行动，不要写“请提供更多信息”。

<a id="resuming-a-previous-session"></a>

## 恢复先前会话

如果 issue 或 PR 已有分流记录，先阅读，检查报告者是否回答了未决问题，在继续前展示更新后的情况。不要重复询问已解决的问题。
