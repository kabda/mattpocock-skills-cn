<a id="codebase-design"></a>

# 代码库设计

设计**深模块**：将大量行为隐藏在小接口之后，把接口放在清晰的 seam 上，并能通过该接口测试。凡是设计或重组代码，都使用这里的语言与原则。目标是为调用方带来杠杆效应、为维护者带来局部性，并让所有人都能轻松测试。

<a id="glossary"></a>

## 术语表

严格使用这些术语：不要替换成 "component"、"service"、"API" 或 "boundary"。保持语言一致正是整个目的。

**模块（Module）**：任何具有接口和实现的事物。刻意不限定规模：可以是函数、类、包或跨技术层的切片。_避免使用_：unit、component、service。

**接口（Interface）**：调用方为正确使用模块必须知道的一切：不仅包括类型签名，还包括不变量、顺序约束、错误模式、必需配置和性能特征。_避免使用_：API、signature（过于狭窄，只指类型层面的表面）。

**实现（Implementation）**：模块内部的内容，即它的代码主体。与**适配器（Adapter）**不同：一个东西可以是实现很大的小适配器（Postgres 仓储），也可以是实现很小的大适配器（内存 fake）。讨论 seam 时用“适配器”，其他时候用“实现”。

**深度（Depth）**：接口处的杠杆效应。调用方（或测试）每学习一单位接口，就能使用多少行为。大量行为隐藏在小接口之后时，模块是**深的**；接口几乎与实现一样复杂时，模块是**浅的**。

**Seam** _（Michael Feathers）_：无需在某处编辑代码，就能改变该处行为的位置；也就是模块接口所在的*位置*。把 seam 放在哪里，是独立的设计决策，与其背后放什么不同。_避免使用_：boundary（与 DDD 的限界上下文含义重叠）。

**适配器（Adapter）**：在 seam 处满足接口的具体事物。描述的是*角色*（填补哪个位置），不是实质（内部是什么）。

**杠杆效应（Leverage）**：调用方从深度中得到的收益。每学习一单位接口，就得到更多能力。一份实现能在 N 个调用点和 M 个测试上带来回报。

**局部性（Locality）**：维护者从深度中得到的收益。变更、bug、知识和验证集中在一处，而不是散布到各个调用方。修复一次，处处生效。

<a id="deep-vs-shallow"></a>

## 深模块与浅模块

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口        │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│       深实现        │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应当避免）：

```
┌─────────────────────────────────┐
│             大接口              │  ← 方法多，参数复杂
├─────────────────────────────────┤
│             薄实现              │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问自己：

- 能减少方法数量吗？
- 能简化参数吗？
- 能在内部隐藏更多复杂性吗？

<a id="principles"></a>

## 原则

- **深度是接口的属性，而不是实现的属性。** 深模块内部可以由小巧、可 mock、可替换的组件组成；只是它们不属于接口。模块既可以有**内部 seam**（对实现私有，供自身测试使用），也可以有位于接口处的**外部 seam**。
- **删除检验。** 想象删除这个模块。如果复杂性消失了，它只是一个透传层。如果复杂性重新出现在 N 个调用方中，它就有存在的价值。
- **接口就是测试面。** 调用方和测试跨越同一个 seam。如果你想*越过*接口测试，模块的形态很可能不对。
- **一个适配器意味着假想的 seam，两个适配器才意味着真实的 seam。** 除非确实有某种变化发生在 seam 两侧，否则不要引入 seam。

<a id="designing-for-testability"></a>

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面要小。** 方法越少，需要的测试越少。参数越少，测试准备越简单。

<a id="relationships"></a>

## 关系

- 一个**模块**恰好有一个**接口**（展示给调用方和测试的表面）。
- **深度**是**模块**的属性，相对于其**接口**衡量。
- **Seam** 是**模块**的**接口**所在的位置。
- **适配器**位于 **seam** 处，并满足**接口**。
- **深度**为调用方带来**杠杆效应**，为维护者带来**局部性**。

<a id="rejected-framings"></a>

## 不采用的表述

- **把深度定义为实现行数与接口行数之比**（Ousterhout）：这会鼓励给实现注水。我们改用“深度即杠杆效应”。
- **把“接口”理解为 TypeScript 的 `interface` 关键字或类的公共方法**：过于狭窄，这里的接口包括调用方必须知道的每一项事实。
- **"Boundary"**：与 DDD 的限界上下文含义重叠。请说 **seam** 或**接口**。
