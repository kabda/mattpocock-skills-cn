# 加深模块

如何结合依赖安全地加深一组浅模块。本文以 [SKILL.md](SKILL.md) 中的词汇为前提：**模块**、**接口**、**seam**、**适配器**。

<a id="dependency-categories"></a>

## 依赖类别

评估加深候选对象时，对其依赖进行分类。类别决定了如何跨越 seam 测试加深后的模块。

<a id="1-in-process"></a>

### 1. 进程内

纯计算、内存状态，无 I/O。总是可以加深：合并模块，直接通过新接口测试。不需要适配器。

<a id="2-local-substitutable"></a>

### 2. 可在本地替代

有本地测试替代品的依赖（用 PGLite 替代 Postgres、内存文件系统）。存在替代品时即可加深。在测试套件中运行替代品，测试加深后的模块。seam 位于内部；模块的外部接口不设置端口。

<a id="3-remote-but-owned-ports--adapters"></a>

### 3. 远程但由自己控制（端口与适配器）

跨越网络边界的自有服务（微服务、内部 API）。在 seam 处定义**端口**（接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/队列适配器。

建议的表达形式：*“在 seam 处定义端口，为生产环境实现 HTTP 适配器，为测试实现内存适配器，这样即使部署跨越网络，逻辑仍集中在一个深模块中。”*

<a id="4-true-external-mock"></a>

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。加深后的模块将外部依赖作为注入端口接收；测试提供 mock 适配器。

<a id="seam-discipline"></a>

## Seam 约束

- **一个适配器意味着假想的 seam，两个适配器才意味着真实的 seam。** 除非至少两个适配器有充分理由存在（通常是生产环境 + 测试），否则不要引入端口。只有一个适配器的 seam 只是间接层。
- **内部 seam 与外部 seam。** 深模块既可以有内部 seam（对实现私有，供自身测试使用），也可以有位于接口处的外部 seam。不要仅仅因为测试使用内部 seam，就通过接口将其暴露出去。

<a id="testing-strategy-replace-dont-layer"></a>

## 测试策略：替换，而非叠加

- 一旦有了针对加深后模块接口的测试，浅模块上的旧单元测试就成了冗余，应当删除。
- 在加深后模块的接口处编写新测试。**接口就是测试面**。
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应当经受得住内部重构，因为它描述的是行为而不是实现。如果实现改变时测试也必须改变，它就是在越过接口进行测试。
