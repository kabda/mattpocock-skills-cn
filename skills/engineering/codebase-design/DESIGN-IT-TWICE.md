# 设计两次

当用户希望为选定的加深候选对象探索不同接口方案时，使用这种并行子 agent 模式。它基于 Ousterhout 的 "Design It Twice"：你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇：**模块**、**接口**、**seam**、**适配器**、**杠杆效应**。

<a id="process"></a>

## 流程

<a id="1-frame-the-problem-space"></a>

### 1. 界定问题空间

启动子 agent 之前，为选定候选对象撰写面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它依赖什么，以及这些依赖属于哪一类（参见 [DEEPENING.md](DEEPENING.md)）
- 用于说明约束的粗略代码草图；它不是提案，只是让约束更具体

将其展示给用户，然后立即进入第 2 步。子 agent 并行工作时，用户可以阅读和思考。

<a id="2-spawn-sub-agents"></a>

### 2. 启动子 agent

并行启动至少 3 个子 agent。每个都必须为加深后的模块产出**截然不同**的接口。

为每个子 agent 提供单独的技术简报（文件路径、耦合细节、[DEEPENING.md](DEEPENING.md) 中的依赖类别、seam 背后是什么）。该简报独立于第 1 步面向用户的问题空间说明。给每个 agent 不同的设计约束：

- Agent 1：“尽量缩小接口：目标是最多 1–3 个入口点。尽量提高每个入口点的杠杆效应。”
- Agent 2：“尽量提高灵活性：支持多种使用场景和扩展。”
- Agent 3：“为最常见的调用方优化：让默认情况轻而易举。”
- Agent 4（如适用）：“围绕端口与适配器设计跨 seam 的依赖。”

在简报中同时包含 [SKILL.md](SKILL.md) 和 GLOSSARY.md 的词汇，让每个子 agent 的命名同时符合架构语言和项目领域语言。

每个子 agent 输出：

1. 接口（类型、方法、参数，以及不变量、顺序和错误模式）
2. 展示调用方如何使用它的示例
3. 实现在 seam 背后隐藏了什么
4. 依赖策略和适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 取舍：哪里杠杆效应高，哪里收益有限

<a id="3-present-and-compare"></a>

### 3. 展示并比较

依次展示设计，让用户逐个理解，然后用文字进行比较。比较维度为**深度**（接口处的杠杆效应）、**局部性**（变更集中在哪里）和 **seam 位置**。

比较后给出自己的推荐：你认为哪个设计最强，以及原因。如果不同设计中的元素可以很好地结合，就提出混合方案。要有明确判断：用户想要有分量的看法，而不是一份菜单。
