<a id="test-driven-development"></a>

# 测试驱动开发

TDD 就是 red → green 循环。本技能是让这个循环产出值得保留的测试的参考：什么是好测试、测试应当放在哪里、有哪些反模式，以及循环的规则。每一节都适用于每一轮循环：在循环开始前及进行中查阅，而不是结束后再看。

探索代码库时，阅读 `GLOSSARY.md`（如果存在），让测试名称与接口词汇符合项目的领域语言，并遵守所修改区域的 ADR。

<a id="what-a-good-test-is"></a>

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变，测试不应因此改变。好测试读起来像规格说明："user can checkout with valid cart"（用户可以用有效购物车结账）准确说明了系统具备的能力；它不关心内部结构，因此能经受重构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

<a id="seams-where-tests-go"></a>

## Seam：测试应当放在哪里

**seam** 是开展测试的公共边界：你在这个接口上观察行为，无需探入内部。测试放在 seam 上，绝不针对内部实现。

**只在事先约定的 seam 上测试。** 编写任何测试之前，写下要测试的 seam，并与用户确认。不在未经确认的 seam 上编写测试。你不可能测试一切，因此事先约定 seam，才能把测试精力投入关键路径和复杂逻辑，而不是每一种边界情况。

询问：“公共接口是什么，应在哪些 seam 测试？”为每个建议的 seam 附一行说明，解释能发现什么、会遗漏什么。

如果接口本身的形态尚未确定（模块有多深、seam 应当在哪里、接口应当暴露什么），用 "codebase-design" 调用 Skill 工具，查阅相关词汇。它是模块、接口、深度、seam、适配器、杠杆效应和局部性等术语的共享来源，是供查阅的参考，而不是要执行的一场会话。

<a id="anti-patterns"></a>

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（查询数据库而不是使用接口）。明显征兆是：行为没有改变，重构却导致测试失败。
- **同义反复**：断言以与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、以相同方式手工推导的快照、断言常量等于自身），因此必然通过，永远不可能与代码产生分歧。期望值必须来自独立的权威来源：已知正确的字面量、推演过的示例或规格说明。
- **横向切片**：先写全部测试，再写全部实现。批量测试验证的是_想象中的_行为：你测试的是事物的_形状_，而不是面向用户的行为；测试对真实变化变得不敏感，而且你在理解实现之前就锁定了测试结构。应当采用**纵向切片**：一个测试 → 一次实现 → 重复，每个测试都是一枚**曳光弹**，根据上一轮循环的发现作出调整。

<a id="rules-of-the-loop"></a>

## 循环规则

- **先 Red，再 Green。** 先编写失败的测试，再只写足够让它通过的代码。不要预想未来的测试，也不要添加推测性的功能。
- **一次一个切片。** 每轮一个 seam、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于审查阶段（参见 `code-review` 技能），而不是 red → green 实现循环。
