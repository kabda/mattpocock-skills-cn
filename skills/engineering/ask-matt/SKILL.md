<a id="ask-matt"></a>

# 询问 Matt

记不住每项技能，就问一问。

**流程**是贯穿各项技能的一条路径。大多数路径沿着同一条**主流程**前进，两条**入口支路**汇入其中。其余技能要么独立使用，要么构成运行在底层的词汇层。

<a id="the-main-flow-idea--ship"></a>

## 主流程：想法 → 交付

大多数工作走这条路线：你有一个想法，希望把它做出来。

1. **`/grill-with-docs`** 通过访谈打磨想法。只要你**在工作目录中开展工作**，就从这里开始：它有状态，会把学到的内容保存在 `CONTEXT.md` 和 ADR 中。（没有工作目录？改用“独立技能”中介绍的 `/grill-me`。两者都运行同一个 `/grilling` 基础技能；`grill-with-docs` 会留下书面记录，因此只要有仓库可存放记录，它就是两者中更好的选择。）
2. **分支：所有问题都能靠对话解决吗？** 如果某个问题需要可运行的答案（状态、业务逻辑，或必须亲眼看到的 UI），就绕道做一个原型，来回都用 **`/handoff`** 衔接（原型位于自己的目录中，这正是 `/handoff` 的用途；参见“阶段边界”）：
   - 用 **`/handoff`** 交出上下文，然后基于该文件打开新会话，
   - 用 **`/prototype`** 编写一次性代码来回答问题，
   - 用 **`/handoff`** 传回所获认识，并在原来的想法会话中引用它。
3. **分支：构建是否需要跨多个会话？**
   - **是** → 先用 **`/to-spec`**（把会话转成规格说明），再用 **`/to-tickets`** 拆成曳光弹工单，每张工单声明自己的**阻塞关系**。本地跟踪器中，每张工单对应 `.scratch/<feature>/issues/` 下一个文件，手动优先处理阻塞项；在真正的跟踪器中，这些关系会变成原生阻塞链接，因此凡是阻塞项都已完成的工单都可以接手：逐张工单启动 **`/implement`**，**每张之间用 `/clear` 清空上下文**。每张工单都自包含，因此上一张的上下文可以丢弃。
   - **否** → 就在这里、同一个上下文窗口中运行 **`/implement`**。

   无论哪条路，**`/implement`** 都在内部驱动 **`/tdd`** 来实现每个 issue（每次一个 red-green 切片），最后在提交前运行 **`/code-review`**，对 diff 做双维度审查（Standards + Spec）。只想先写测试来构建某项具体行为、无需完整规格说明时，单独使用 **`/tdd`**；想相对固定基点审查分支或 PR 时，单独使用 **`/code-review`**。

<a id="context-hygiene"></a>

### 上下文管理

步骤 1–3 保持在**同一个连续的上下文窗口**中（完成 `/to-tickets` 前不要压缩或清空），让追问、规格说明和工单都建立在同一套思考之上。之后每次 `/implement` 都从工单出发，以全新上下文开始。

限制因素是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口范围（前沿模型约为 150k tokens）。如果在 `/to-tickets` 之前会话就接近这个范围，不要在能力下降后硬撑；在最近的阶段边界执行 `/compact`，再继续（参见“阶段边界”）。

<a id="on-ramps"></a>

## 入口支路

从某种情境出发，产生工作，再汇入主流程。

- **Bug 和请求堆积** → **`/triage`**。它推动 issue 流转经过各个分流角色，产出 agent 可直接接手的 issue，随后由 **`/implement`** 处理。

  分流仅适用于**不是你创建的** issue：bug 报告、收到的功能请求，以及任何未经整理的输入。`/to-tickets` 生成的工单已经适合 agent 接手，**不要再对它们做分流**。

- **某处出故障了** → **`/diagnosing-bugs`**。用于棘手问题：一眼看不出原因的 bug、间歇性失败、在两个已知正常状态之间悄然出现的回归。没有**紧凑反馈循环**（一条已能因*这个* bug 变 Red 的命令）之前，它拒绝推测；之后用回归测试来修复。如果复盘发现真正的问题是没有合适的 seam 来锁定 bug，它会转交 **`/improve-codebase-architecture`**。

- **庞大且模糊的工作：全新项目或大型功能，一个会话装不下** → **`/wayfinder`**，这是这里认知负荷最高的流程。当从当前位置到目标的道路还看不清时，它会在 issue 跟踪器上绘制由**决策工单**组成的**共享地图**，逐一解决，产出**决策，而非交付物**，直到迷雾退去、道路清晰。**`/grill-with-docs`** 打磨的是一个会话容得下的想法，而 wayfinder 用于容不下的想法；它更慢、更密集，因此只在这种情况下使用，绝不要用于范围已明确的功能。

  地图清晰后，**它会交接，不会构建**：从 **`/to-spec`** 汇入主流程，把地图中相互链接的决策收敛为可实施的计划，再照常运行 `/to-tickets` 和 `/implement`。直接把地图接到 `/implement` 会跳过这个收敛过程，丢失链接中的细节；只有工作最终确实很小时，才直接进入 `/implement`。

<a id="codebase-health"></a>

## 代码库健康

不是功能开发，而是日常维护。

- 有空时就运行 **`/improve-codebase-architecture`**，让代码库保持适合 agent 工作的状态。它会发现**深化机会**；选中一个就会*产生一个想法*，可以从 `/grill-with-docs` 带入主流程。它是寻找候选项的调查工具；下面的 **`/codebase-design`** 则是设计选中项的工作台。

<a id="vocabulary-underneath"></a>

## 底层词汇

两项由模型调用的参考技能运行在其他技能*之下*，各自是所用词汇的唯一权威来源。问题出在**用词**而非流程时，直接调用；也可以让上面的技能按需引入。

- **`/domain-modeling`**：打磨项目的*领域*语言：质疑模糊术语，厘清一词多义（比如 "account" 承担三种含义），把难以逆转的决策记为 ADR。它是 `/grill-with-docs` 主动运用的实践，用来保持 `CONTEXT.md` 作为清晰的术语表。
- **`/codebase-design`** 提供设计模块*形态*的深模块词汇（模块、接口、深度、seam、适配器、杠杆效应、局部性）：在清晰的 seam 处，用小接口封装大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套词汇。

<a id="phase-boundaries"></a>

## 阶段边界

**阶段**是会话内的一段工作：追问、实现、QA。两个阶段之间的**边界**有五种选择，如何选择是这张地图里最模糊的决策：

- **继续（Continue）**：留在原处。没有成本，也没有损失。
- **`/clear`**：当当前内容对下一步都不重要时，清空窗口。
- **`/handoff`** 写出可携带的 Markdown 文件。用途很窄：仅限切换到**新的 harness**、**新目录**、交给**同事**，或在**阶段中途**分出旁支任务。它带来的是可携带性。
- **子 agent**：把范围明确的任务送到独立窗口，取回报告。
- **`/compact`** 压缩当前上下文，用它启动新会话。这是**默认选择**，位于决策树底部，而非最先尝试的选项。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序决策树：五个问题、每条分支的理由，以及为什么失去一手来源的代价使**继续**成为首先应当排除的选项。应当**在**边界处决策；阶段中途则继续，或把剩余工作拆给子 agent。

<a id="standalone"></a>

## 独立技能

完全位于主流程之外。

- **`/grill-me`**：与 `/grill-with-docs` 一样持续追问，但**无状态**：不在本地保存任何内容，也不构建 `CONTEXT.md`。当你**不在工作目录中工作**时使用（打磨计划、设计、文章，或任何没有仓库承载的内容）。如果在工作目录中，改用 `/grill-with-docs`：它执行同样的访谈，还留下书面记录，因此严格来说更好。
- **`/grilling`** 是访谈基础技能本身：轮次、前沿，事实由 agent 查明、决策由你作出。`/grill-me` 和 `/grill-with-docs` 是两个命名入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部使用它。只有想要没有外层包装的访谈时，才直接调用。
- **`/resolving-merge-conflicts`** 逐块处理正在进行的 merge 或 rebase 冲突，通过追溯双方一手来源的**意图**来解决，而非挑选代码行，随后完成操作。它绝不运行 `--abort`。这是所有流程之外的独立技能：已经身处冲突时使用。
- **`/prototype`** 是回答一个设计问题的小型一次性程序：这个状态模型是否合适，或 UI 应该长什么样。一次性约束的是代码写法，并非承诺销毁代码：答案会融入正式代码，原型本身则作为**一手来源**保留在 main 之外的 `prototype/<name>` 分支，并由实现 issue 引用。它是主流程步骤 2 的支路，但任何难以在纸面上解决的设计问题都可以使用。
- **`/research`**：把阅读调查委派给**后台 agent**：它依据**一手来源**调查问题，再在仓库留下带引用的 Markdown 文件。它阅读时你可以继续工作。产出的文件可以从 `/grill-with-docs` *带入*主流程，因为研究为思考提供材料，而不代替思考。
- **`/to-questionnaire`** 用于阻碍你的信息既不在你脑中、也不在代码库中，而在**别人脑中**的情况；它会为对方编写问卷。它与 `/grill-me` 相反：不是就主题访谈你，而是就**发送安排**（发给谁、需要什么回复）访谈你，再围绕信息缺口设计问题。收回的内容可以作为 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`/wizard`** 用于只有**人**才能完成的步骤：开通基础设施、设置凭据或 CI secrets、操作陌生第三方控制台、执行一次性迁移或切换。它生成交互式 bash 脚本，逐个打开 URL、收集值并写入 `.env` 和 GitHub secrets，让这套流程不必每次都重新向 agent 解释。它由模型调用，因此 agent 一遇到只有你能跨过的障碍就会使用。如果 agent 能自己做，就应当自己做；这个技能用于确实需要人参与的地方。
- **`/wait-what`** 用于纠正没讲明白的消息。可在任何技能执行期间、对话中途使用，agent 会用通俗英语和 `CONTEXT.md` 词汇重新解释刚才的话，补上你缺少的上下文。它是事后补救；`/grill-with-docs` 则是事前预防，因为及早约定共享语言，才能从根本上避免突如其来的术语。
- **`/teach`**：跨多个会话学习一个概念，使用当前目录作为有状态工作空间。
- **`/writing-for-agents`** 是编写 agent 所消费文档的参考：技能、AGENTS.md，以及被引用的文档。

<a id="precondition"></a>

## 前置条件

**`/setup-matt-pocock-skills`**：首次运行工程流程前执行，配置其他技能所依赖的 issue 跟踪器、分流标签和文档布局。也支持自定义 issue 跟踪器。
