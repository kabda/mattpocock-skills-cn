本技能利用当前对话上下文和对代码库的理解，产出规格说明。不要访谈用户；只综合整理已经知道的内容。

你应当已经获得 issue 跟踪器和分流标签词汇。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

<a id="process"></a>

## 流程

1. 如果尚未探索仓库，先探索以了解代码库当前状态。整份规格说明都使用项目领域术语表中的词汇，并遵守所涉及区域的 ADR。

2. 勾勒将在哪些 seam 上测试功能。优先使用已有 seam，而不是新增。使用尽可能高层的 seam。如果需要新 seam，就在所能选择的最高位置提出方案。代码库中的 seam 越少越好，理想数量是一个。

与用户核对这些 seam 是否符合预期。

3. 按下面的模板编写规格说明，然后发布到项目 issue 跟踪器。添加 `ready-for-agent` 分流标签，无需额外分流。

<spec-template>

## Problem Statement

从用户视角描述用户面对的问题。

## Solution

从用户视角描述问题的解决方案。

## User Stories

一份很长的、带编号的用户故事列表。每个用户故事应当采用以下格式：

1. 作为 <actor>，我希望有 <feature>，以便 <benefit>

<user-story-example>
1. 作为手机银行客户，我希望查看各账户余额，以便对支出作出更明智的决定
</user-story-example>

这份用户故事列表应当极其详尽，覆盖功能的所有方面。

## Implementation Decisions

列出已经作出的实现决策。可以包括：

- 将要构建／修改的模块
- 这些模块中将要修改的接口
- 开发者给出的技术澄清
- 架构决策
- schema 变更
- API 契约
- 具体交互

不要包含具体文件路径或代码片段。它们可能很快过时。

例外：如果原型产出的片段能比文字更精确地表达决策（状态机、reducer、schema、类型结构），就在相关决策中内联该片段，并简要注明来自原型。裁剪到承载决策的部分，不要提供可运行的完整演示，只保留重要部分。

## Testing Decisions

列出已经作出的测试决策。包括：

- 描述什么是好测试（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 可参考的既有测试（即代码库中类似类型的测试）

## Out of Scope

描述不属于本规格说明范围的事项。

## Further Notes

关于该功能的其他说明。

</spec-template>
