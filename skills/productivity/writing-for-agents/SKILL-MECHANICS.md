# 技能机制

这是 [`writing-for-agents`](SKILL.md) 中技能专属的分支：文档是技能时，有哪些变化（frontmatter、调用选择、路由技能）。其余写作方法都属于 `SKILL.md` 中的通用参考。

<a id="invocation"></a>

## 调用

两种选择，在两种负荷之间取舍：

- **模型调用**的技能保留 `description`，因此 agent 能自主触发，其他技能也能调用。你仍可以输入其名称：模型调用始终*包含*用户调用能力；description 只会增加 agent 的发现能力，从不移除人的调用能力。description 是技能的顶层上下文指针，被迫始终加载：以永久上下文负荷换取可发现性。正文全部为参考的模型调用技能，也是共享参考的一种归宿：其他技能可以调用它，让多项技能所需的参考只存在于一个地方。机制：省略 `disable-model-invocation`，编写面向模型、包含触发分支的 description（完整适用 `SKILL.md` 的指针写作规则）。
- **用户调用**的技能把 description 从 agent 可访问范围移除：只有人输入名称才能调用，其他技能不能调用。上下文负荷为零，但消耗认知负荷：你就是必须记得它存在的索引。机制：设置 `disable-model-invocation: true`；`description` 变成面向人的一行摘要，去掉触发条件列表。

只有 agent 必须自主访问，或另一项技能必须调用时，才选择模型调用。如果永远只靠手动触发，就设为用户调用，不付上下文负荷。

两项用户调用技能共同需要的参考，不能放在任何一项内部：没有 description，它们无法互相触发。把它移到技能系统之外的普通文件：任何技能都能指向的外部参考。

<a id="splitting-by-invocation"></a>

## 按调用拆分

这是按调用来切分文档（按顺序切分见 `SKILL.md`）：如果有一个独立引导词应自主触发它（你确实会在提示词中使用的触发词），或另一项技能必须调用它，就拆出一项模型调用技能。新增的始终加载 description 会带来上下文负荷，因此这种独立访问能力必须值得其成本。

<a id="router-skills"></a>

## 路由技能

用户调用技能多到记不住时，积累的认知负荷可由**路由技能**缓解：用一项用户调用技能列出其他技能及其适用时机，让人只需记住一项，而非多项。它只能提示，不能触发它们：用户调用技能没有 description，因此只有人能调用。
