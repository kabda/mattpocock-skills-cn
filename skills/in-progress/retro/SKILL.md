用户要求进行**复盘**。你要提出对编码 agent **环境**的改进建议，以改善未来运行。

<a id="steps"></a>

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents`，获取写作风格指南。

2. 阅读用户指定会话的一手来源，可能需要搜索本机会话日志。用户未指定时，默认当前会话。

3. 在以下类别中寻找改进候选项。

- **导航**：agent 找到正确文件有多容易？文件间是否有隐藏依赖？**导航指针**能否使其更容易？会话花了很久寻找某条信息时*使用*。
- **自动检查**：有没有能捕获 agent 所犯错误的自动检查？Lint、类型检查、测试、文件系统 linter？先读仓库自己的检查命令（`package.json`/构建工具的 `lint`/`check` 脚本及 CI workflow），这样已有却未接入或悄悄失效的检查会成为发现，而非重新发明。仓库没有**护栏**（没有运行 lint/typecheck/test 命令的 pre-commit hook，也没有 CI job）本身就是一个发现：未经 lint 的仓库是长期错失机会，不是中性默认值。agent 犯了自动检查本可捕获的错误，或仓库完全没有护栏时*使用*。
- **编码标准**：是否应给**审查 agent**新增一条执行规则？是否应删除或澄清已有规则？先分类违规：**机械性**违规（固定语法模式、禁止的 API、导入形态、文件位置规则）就必须用确定性检查，仅此而已：仓库自身 linter 的自定义规则、新 pre-commit hook 或新 CI job，按仓库语言和已有护栏选择成本最低的方式。默认构建检查，而非写规则。`CODING_STANDARDS.md` 留给真正的**判断取舍**（跨文件一致性、“符合周围风格”，以及任何护栏都无法替代的事项）。审查 agent 漏掉错误时*使用*。
- **全局 AGENTS.md**：有没有引导指令应移到编码标准（或自动检查）中？仓库或用户全局范围的 AGENTS.md 特别大时*使用*。
- **工具开销**：agent 是否发出了可精简的昂贵工具调用？是否有自定义工具（CLI、MCP）特别浪费 tokens？agent 发出昂贵工具调用时*使用*。
- **No-op**：寻找引导文件中不改变 agent 行为的指令。引导文件庞大笨重时*使用*。
- **信息访问**：寻找增加 agent 信息访问能力的机会。例如用 tee 保存开发服务器日志、第三方服务只读访问。agent 无法获得关键信息时*使用*。

4. 按严重程度排序，向用户展示候选项。

## 参考

<a id="implementation-vs-review"></a>

### 实现与审查

记住，所有工作都经过两个阶段：实现和审查。实现 agent 的**上下文压力**最大，负责探索、编码和调试失败。

审查 agent 的上下文压力最小：它收到 diff，无需探索，也经常无需编码或调试。

因此，应由审查 agent 负责落实编码标准，而非实现 agent。

<a id="files"></a>

### 文件

你可以访问仓库中的多个文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被放入所有在本仓库工作的 agent 的上下文窗口。应极其克制地使用，通常只放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：审查时读取，实现时不读。标准文件超过 1,000 行时，添加指向 docs 文件夹的**导航指针**。
- 文档：把 docs 用作由其他文件指向的参考文件。写新文档前先找已有文档。
- 技能：用技能承载文档（因为 description 会进入 agent 上下文窗口），或承载用户调用命令。遵循 `writing-for-agents` 技能中的建议。
