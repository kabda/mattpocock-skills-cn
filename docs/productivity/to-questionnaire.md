<a id="what-it-does"></a>

## 它能做什么

`to-questionnaire` 将你无法独自确定的决策转成一份**问卷**：一份 Markdown 文档，交给掌握你所缺信息的那个人，让对方异步填写，或由你们在会议中共同完成。

它追问的是**发送安排**，绝不是主题本身。在这里，就主题访谈你毫无意义：正因为不了解，才需要写给别人。因此它只问两个你始终能回答的问题（发给谁，需要对方返回什么），并让文档中的每个问题都针对两者之间的**缺口**。

<a id="when-to-reach-for-it"></a>

## 何时使用

输入 `/to-questionnaire` 调用它；[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不会自行使用。

当一项决策被另一个人头脑中的知识阻塞时使用：客户、领域专家、掌握业务规则的高管，或你所在团队之外的同事。该选哪个技能，取决于答案实际上在哪里：

| 答案在…… | 使用 |
| --- | --- |
| 你自己脑中，尚未明确 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库中 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人脑中 | `to-questionnaire` |
| 还不在任何人脑中，需要先有东西可供观察和反馈 | [prototype](https://aihero.dev/skills-prototype) |

常见场景是一场[追问](https://www.aihero.dev/ai-coding-dictionary/grilling)会话停滞：浮现的某些问题不由你回答。在同一段对话中运行 `/to-questionnaire`，把这些问题带到线下，再把答案带回来继续。

<a id="the-send-not-the-subject"></a>

## 发送安排，而非主题本身

访谈只有两次交流，然后停止。

- **发给谁？** 对方的角色、专业知识、与你的关系。这决定语气和文档需要携带多少背景：外部客户需要引导，同组同事则不需要。
- **需要对方返回什么？** 你无法独自确定的具体决策或事实。这会成为衡量最终文档的检查清单：你列出的每一项，都有一个针对它的问题。

之后全部是起草工作。文件写入当前目录的 `to-questionnaire-<slug>.md`。不需要设置、工作区，也没有需要配置的内容。

<a id="the-document"></a>

## 文档

文档被定位为**发现型问卷**（你缺少背景，接收者掌握背景），这个定位决定了其形式：

- 一行目的说明，指出哪项决策依赖它；再给不了解你想法的接收者一段简短背景。
- 问题按**最重要的在前**排序，并按主题标题分组，因为异步意味着可能只有一次机会。
- 每个问题一个想法，绝不混合多个问题；下方留出回答位置，只有可能被误读时才加一行*为什么重要*。
- 明确允许回答“我不知道”：标出的不确定性有价值；写得像事实的自信猜测没有。
- 最后用一个兜底问题收尾：还有哪些我们没问到、但应当知道的事情？

它刻意不做两件事。第一，不做**分支问卷**：问题是平铺、分组的列表，不是回答 A 后跳过 D 节的树。第二，不面向**多个接收者**：一次运行给一个人生成一份文档。

<a id="common-questions"></a>

## 常见问题

**它会读取追问会话，并从中提取问题吗？**
没有独立的这一步。技能没有输入摄取阶段：先问发送安排，然后起草。它之所以能接在追问会话后工作，是因为你在**同一段对话**中运行，因此[会话](https://www.aihero.dev/ai-coding-dictionary/session)已经位于[上下文](https://www.aihero.dev/ai-coding-dictionary/context)中，起草时可以利用。如果在新会话启动，它对之前的追问一无所知；回答“需要对方返回什么？”时，你就要自己重新提供主题。

**缺少的答案不全在同一个人那里，能按接收者拆分吗？**
不能。第 1 步询问的是单数的*接收者*，整份文档的语气和背景都针对该人。如果三个人各掌握答案的一部分，就运行三次，每人一次。按专业或角色在单份文档内部路由问题，确实有人请求过；但当前提供的不是这个功能。

**问题之间有依赖吗？会根据前面的回答跳过某些章节吗？**
不会。依赖式问题设计曾被探索，但没有交付。输出是静态文档：按主题分组、最重要的在前、每个问题都有效。反对分支设计的理由很合理：[模型](https://www.aihero.dev/ai-coding-dictionary/model)在得到真实答案之前，若提前规划超过两三个问题，效果就不好；而分支文档要求在得到任何答案之前，预先规划全部问题。

**如果接收者也不知道呢？**
文档会要求对方直说。它明确接受“我不知道”和部分答案；标出的不确定性比猜测更有价值，因为一旦回到你的上下文，含糊的答案和自信但错误的答案看起来没有区别。

**它会发送到任何地方吗（Slack、issue 跟踪器、电子邮件）？**
不会。它只在当前目录写入 Markdown 文件，并告诉你路径。传递由你负责：粘贴进[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)、放到 Slack 对话中、作为邮件附件，或在共享屏幕上打开共同填写。这四种方式都有人手动接通过。

**这不就是批量模式的 `/grill-me` 吗？**
不是，应当记住区别。`grill-me` 已经按**轮次**提问：一次问完整个前沿，再根据你的回答重新计算，因此“一次给我全部问题”的需要已经由它满足。`to-questionnaire` 关注的是另一维度：不是问题如何呈现，而是答案在谁脑中。更快地自己回答，用 `grill-me`；从别人那里问出答案，用本技能。

**不用技能，直接让 agent 做不就行了？**
可以，而且在它出现之前，很多人就是这样做的：`OPEN_QUESTIONS.md` 文件、发给客户的电子表格，或为每个未回答问题创建一张“需要更多信息”的工单。本技能带来两点价值：访谈不会偏到主题本身，文档的形式也适合非技术接收者真正填写。如果你已有有效的内部格式，坦诚地说，就不需要本技能。

<a id="its-working-if"></a>

## 如何判断它有效

- 它询问接收者和你需要对方返回什么，然后停止提问。如果问到主题本身，就是偏离了技能要求。
- 你列出的每项“需要对方返回的内容”，都能追溯到文件中的一个问题。
- 问题针对的是*接收者*知道的内容，而不是逐字抄下你自己的未决问题。
- 把文件交给没参与对话的人，对方也能知道为什么收到它、何时需要回复。
- 返回的答案可以作为下一轮追问的有效输入，而不是又带回一组新问题。

<a id="where-it-fits"></a>

## 它在流程中的位置

`to-questionnaire` 是随时可用的独立工具。它位于你自身知识的边界：下一步需要的是另一个人，而不是另一个技能。最常见于流程中途，规划因为不由你决定的事项而停滞。

它的相邻技能是 [grill-me](https://aihero.dev/skills-grill-me)，两者按答案所在位置分工：追问挖掘你，问卷挖掘别人。返回的是原始材料：把它投入另一轮追问；如果工作将进入构建，也可以交给 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。不确定此刻哪个技能适合时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你指路。
