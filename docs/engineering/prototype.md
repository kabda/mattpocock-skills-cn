<a id="what-it-does"></a>

## 它能做什么

`prototype` 编写**用来回答一个问题的一次性代码**：这个状态模型感觉对吗，或者这个界面应该是什么样子。问题先行，决定后续一切的形式；回答错误问题的原型，无论多好看，都是纯粹的浪费。

“一次性”约束的是代码*如何编写*，不是承诺销毁它。不写测试，不做超出可运行所需的错误处理，不做抽象，不持久化，因为这些都不能帮助你学到那个正在探究的唯一问题。最终保留的是融入真实代码的答案，以及放在 main 之外分支上的原型本身，作为答案的来源证据。

<a id="when-to-reach-for-it"></a>

## 何时使用

输入 `/prototype`，或者在任务适合时由 [agent](https://www.aihero.dev/ai-coding-dictionary/agent) 自动使用。

遇到无法靠讨论解决的问题时，立即使用：状态机的边界情况太多，脑中装不下；一个界面要看到三个版本并排比较才想象得出来。[追问](https://www.aihero.dev/ai-coding-dictionary/grilling)会话恰恰会在这些问题上膨胀：agent 换种说法，你继续猜测，范围随着不确定性扩大。停止追问，构建一次性版本，看一看，再用一句话回答。如果是已经构建的内容行为不正常，想知道原因，就使用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)；原型探索的是要构建什么，而不是已构建的东西为什么坏了。

你也可能并非主动选择，却来到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在地图上登记 `prototype` 类型的决策[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，处理这种工单就是运行本技能。

<a id="two-branches"></a>

## 两个分支

问题决定分支，而两个分支产出的交付物差异很大：

- **“这个逻辑／状态模型感觉对吗？”**：一个**可共享的单 HTML 文件**。自包含页面，不需要构建或服务器，双击就能打开。它包含每次点击后都会重新渲染的带标签状态面板、供人按任意顺序试探模型的自由操作按钮，以及分标签页的**引导演练**（每页一个场景，下方按顺序列出要按的按钮）。所有标签都使用领域语言，因此可以交给设计师、PM 或领域专家，让他们亲自感受模型。页面背后的逻辑是一个不接触 DOM 的小型纯模块（reducer、状态机、一组函数），便于将已验证版本直接提取到真实代码中。
- **“它应该是什么样子？”**：同一路由上的几个**截然不同**的 UI 变体，通过底部悬浮栏和 `?variant=` URL 参数切换。变体必须在结构上有分歧，而不只是颜色；三个稍作调整的卡片网格是墙纸，不是原型。尽可能在真实页面内呈现，面对真实数据和真实信息密度，因为在真空中评判的变体总显得不错。

两者都将状态保存在内存中，启动无需思考，每一步之后都展示完整状态。一旦发现自己开始加固原型（添加测试、连接真实数据库、为将来可能需要的情况泛化），就已经不再是在做原型。

<a id="the-prototype-is-a-primary-source"></a>

## 原型是一手来源

完成的原型留下两样东西，分别去往不同位置。

**答案**（结论及其解决的问题）会被持久记录：提交信息、ADR、实现 issue。这是主分支保留的内容，融入真实代码。

**原型**是答案来源的可运行证据，不会被删除。它也不属于 main：没有需要在那里维护的东西，而且会迅速腐化。因此，它被提交到 main 之外的一次性 `prototype/<name>` 分支，永不合并，并在实现 issue 上留下指向该分支的[上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。Main 保持干净；探索过程仍可找到，接手工作的人也能重新运行。

<a id="common-questions"></a>

## 常见问题

**等等，原型不是应该删除吗？**
现在不是了。以前确实如此：构建、保留答案、丢掉代码。对此最有力的反对意见从来不是速度，而是*下一场[会话](https://www.aihero.dev/ai-coding-dictionary/session)谁来接手，他们凭什么继续？* 原型的文字摘要会丢掉让它有说服力的东西。因此，现在原型被视为[一手来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)：放到 main 之外的 `prototype/<name>` 分支，实现 issue 指向它。改变的是代码存放位置，不是纪律；它仍然绝不合并进 main。

**以前会构建终端应用，现在去哪了？**
逻辑分支如今改为输出一个可共享的单 HTML 文件。终端应用只能由克隆了仓库、安装了运行环境的人操作，恰恰排除了原型需要征求意见的人：设计师、PM、知道状态模型应当表达什么的领域专家。一个双击即可打开、也能通过邮件传递的自包含文件，任何人都能操作。底下的纯逻辑模块没有改变，仍然是提取到真实代码中的部分。

**明明该实现了，agent 却叫我运行 `/prototype`。**
这是已知问题，根源在命名。`prototype` 是一个通用、吸引人的词，对不了解流程的 agent 来说，工单存在之后它像是“显而易见的下一步”，所以即使设计已在对话中完全确定，也会按名称推荐它。如果已经知道要构建什么，下一步就是逐工单运行 `/implement`。只有某个具体设计问题确实未决、又无法靠讨论解决时，才使用原型。

**是否应当在构建任何生产功能之前，先给整个应用做原型（例如向潜在客户演示）？**
那是借用了本技能名称的另一种交付物。这里的原型只针对一个问题，而“整个应用是什么样”不算一个问题。完整应用原型没有自然停止点，于是会靠惯性变成生产应用：清理阶段始终没发生，按原型规则编写的代码（无测试、无错误处理）最终出现在用户面前。如果需要销售演示，就明确按演示来构建，并说明其中没有生产代码。如果需要确定设计问题，就把范围缩到那个问题。

**如何在独立会话中运行？**
原型位于自己的目录，会生成大量你不想放进提问对话的[上下文](https://www.aihero.dev/ai-coding-dictionary/context)，所以在别处运行，只带回答案。[handoff](https://aihero.dev/skills-handoff) 是双向桥梁。

**这难道不是烧 token 最快的方式吗？**
如果对本可讨论清楚的问题做原型，或让一个原型蔓延到整个功能，确实可能如此。真正有意义的比较不是 token 与零，而是 [token](https://www.aihero.dev/ai-coding-dictionary/token) 与另一种代价：构建错误的状态模型，直到已有生产调用方才发现。保持问题狭窄、运行短暂，开销就会相称。

<a id="its-working-if"></a>

## 如何判断它有效

- 能用一句话说清原型要回答的问题，并把它写在演示顶部，而不只是记在脑中。
- 不读代码的人也能操作逻辑演示。他们打开文件、按演练标签页里的按钮，并用自己的话描述所见。
- 有人说“等等，这不应该能发生”或“咦，我原本以为 X”。这是*想法*中的 bug，正是全部目的。
- UI 变体在布局和信息层级上不同，而不只是颜色和文案；收到的反馈是“B 的页头加 C 的侧栏”。
- 一次坐下来就能得到答案。如果一天后还在构建，问题就太大了，应当拆分。
- 结束时，main 包含决策，没有任何原型代码；实现 issue 指向仍保存原型的分支。

<a id="where-it-fits"></a>

## 它在流程中的位置

`prototype` 是**随时可用的独立工具**：进入它以解决一个设计问题，然后退出；它同时也是其他技能运行所依赖的能力。

最大的使用方是 [wayfinder](https://aihero.dev/skills-wayfinder)。Wayfinder 地图由**决策工单**组成，`prototype` 是四种工单类型之一：当阻塞问题是“应该是什么样子”或“应该如何表现”、再多讨论也无法解决时使用。Wayfinder 通过做出可供反馈的具体事物，提高模糊讨论的细致程度；本技能负责构建这个具体事物。原型工单由答案解决，原型则作为资源从地图中链接。

其他相邻技能位于其上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答能靠追问解决的问题；不能的来到这里，再把一句话答案带回访谈。下游，已验证的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的已确定输入，后者可以内联原型产出的承载决策的片段，而不必用文字重新描述。其他情况，[ask-matt](https://aihero.dev/skills-ask-matt) 会在整套技能中为你指路。
