<a id="what-it-does"></a>

## 它能做什么

`diagnosing-bugs` 对棘手 bug 或性能回归执行六阶段诊断：构建复现、最小化、排列假设、埋点、通过回归测试修复、清理。

在建立**紧凑**反馈循环之前，它不允许 agent 形成理论：必须有一条明确命名、已经运行过一次的命令，能因*这个* bug 变 Red，并在修复后变 Green。编码 agent 收到 bug 报告后，默认会读代码并猜测；本技能阻止这种做法。如果没有能变 Red 的命令，就没有阶段 2。这一道门槛就是本技能存在的目的。信号一旦存在，之后的一切（二分、假设检验、埋点）都是机械工作。

<a id="when-to-reach-for-it"></a>

## 何时使用

输入 `/diagnosing-bugs`，或者在任务适合时由 agent 自行使用：它可由模型调用，触发词包括 "diagnose" / "debug this"，也会因报告某处损坏、抛错、失败或变慢而触发。

在棘手问题上使用：初看难以定位的 bug、间歇性不稳定问题、在两个已知正常状态之间悄悄出现的回归。它刻意采用重流程，不适合你只想用一条消息得到答案的问题。

| 你的情况 | 去哪里 |
| --- | --- |
| 能用症状描述的具体缺陷 | 本技能 |
| 缓慢端点，或已知前后对比的耗时回归 | 本技能：它有性能分支（测量基线，再二分） |
| “这个代码库的瓶颈在哪里？”，没有具体症状 | 不适用。它诊断一个已知失败，不做审计 |
| 他人提供的原始 bug 报告，尚未确认或整理 | 先用 [triage](https://aihero.dev/skills-triage) |
| 用一次性代码回答设计问题，而不是追查缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 以测试优先方式构建计划中的行为 | [tdd](https://aihero.dev/skills-tdd) |
| 不存在能通过测试锁定 bug 的合适 seam | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)：本技能会自行交接到那里 |

<a id="the-tight-loop-is-the-skill"></a>

## 紧凑循环就是本技能的核心

阶段 1 获得远高于其他阶段的投入，因为它是唯一困难的阶段。技能给出了构建循环的一系列方法，大致按优先顺序排列：

1. 在能触及 bug 的任意 seam 上编写失败测试。
2. 针对运行中的开发服务器编写 curl 或 HTTP 脚本。
3. 使用 fixture 输入执行 CLI 调用，与已知正确的快照比较。
4. 用无头浏览器脚本断言 DOM、控制台或网络。
5. 重放捕获材料：保存请求、payload 或事件日志，隔离执行相关代码路径。
6. 一次性测试环境：系统的最小子集，通过一次函数调用运行。
7. 针对“偶尔输出错误”的属性测试或 fuzz 循环。
8. 可以交给 `git bisect run` 的二分测试环境。
9. 差分循环：相同输入，对比旧版与新版。
10. [人在循环中](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)的 bash 脚本，作为最后手段。技能为此附带 `scripts/hitl-loop.template.sh`：agent 运行脚本，你在终端中按提示操作，答案以可解析输出返回。

目标不是拥有*一个*循环，而是**紧凑**：快速（秒级）、确定（每次结论相同）、准确（断言你的确切症状，而不是“没崩溃”），且 agent 能无人值守运行。30 秒且不稳定的循环几乎不比没有强。对于只偶尔出现的 bug，目标不是一次干净复现，而是**更高的复现率**：循环触发、并行、加压、注入 sleep，直到发生率足够高，能够调试。

确实无法构建循环时，指令要求它停下来明确说明，列出尝试过的方法，并向你请求[环境](https://www.aihero.dev/ai-coding-dictionary/environment)访问权限、捕获材料，或添加临时埋点的许可。它不应仍然继续提出假设。

<a id="the-gates-between-phases"></a>

## 阶段之间的门槛

各阶段是关卡，不是检查清单。只有具体条件成立，下一阶段才会开启。

| 关卡 | 必须满足什么 |
| --- | --- |
| 进入阶段 2 | 一条明确命名、已经运行并连同输出展示的命令，能够因这个 bug 变 Red |
| 进入阶段 3 | 已经复现*并且*最小化：剩余每个元素都不可或缺 |
| 进入阶段 4 | 有 3–5 个已排序、可证伪的假设，每个都说明预测，且在测试任何假设前先展示给你 |
| 进入阶段 5 | 探针对应具体预测，一次一个变量，每条调试日志都带有类似 `[DEBUG-a4f2]` 的标记，便于一次 grep 清理 |
| 完成 | 原始复现不再复现，埋点已移除，最终正确的假设已写入提交信息 |

阶段 5 有一个值得了解的例外。回归测试要在修复之前写，但只有存在**正确的 seam** 时才写：它必须让测试按调用点实际发生的方式，执行真实 bug 模式。如果唯一可用的 seam 太浅，技能被要求明确说明，而不是写一个制造虚假信心的测试。缺少 seam 本身就是发现，也正是将复盘导向 `improve-codebase-architecture` 的原因。

<a id="common-questions"></a>

## 常见问题

**我只想要直接答案的简单问题，也会触发它。**
这是本技能被报告最多的问题，而且确实存在。尤其是在 GPT-5.6-Sol 上，用户报告普通的问题描述就会触发它：“模型转而触发相当正式的 diagnosing-bugs 技能。然后在给我回复或建议之前，先构造复现场景（常常是价值有限的 mock 场景），造成相当明显的回复延迟。”四个不同的人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 中报告了相同情况。已接受的修复方向是先采用较轻的方法，只有问题确实需要时才升级为重流程，但变更尚未落地。技能按 Claude Code 的调用行为校准；触发门槛更低的[模型](https://www.aihero.dev/ai-coding-dictionary/model)会过度调用。在分级机制落地之前，实际应对办法是明确说出需要（"just answer this, don't diagnose"，即只回答，不要诊断），或在 [agent 运行环境](https://www.aihero.dev/ai-coding-dictionary/harness)中禁用它的模型调用。

**能让它查看代码库，找出性能问题在哪里吗？**
不能。它诊断的是一个你已经能指明的失败。性能分支针对有症状的回归（建立基线测量，再二分，先测量后修复），不用于主动全面排查。主动排查版本的技能曾被[提议并关闭](https://github.com/mattpocock/skills/issues/431)；目前没有对应技能。

**写修复之前，它会停下来问我吗？**
不会。只有阶段 3 设有人类检查点：任何假设被测试之前，先向你展示排序后的列表；如果你不在，它会按自己的排序继续。埋点与修复之间没有关卡，因此你尚未认同根因时，agent 就可能开始写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 请求增加这道关卡，目前仍未解决。如果需要，请在调用技能时说明。

**我已经对这个 bug 报告运行过 `/triage`，这是重复工作吗？**
部分是，但两个技能都没有承认。正如一位读者所说：“Triage 的第 3 步本质上就是 diagnosing-bugs 阶段 1–2 的浅层、有限版本，但两个文件都没有提到对方。”Triage 做有限范围的“这真的是 bug 吗、涉及什么范围”检查；本技能做彻底版本。先运行 triage 并不浪费（其验证通常提供阶段 1 所需的大部分原始材料），但要预期在这里重新认真执行，而且不会有交叉引用提醒你这一点。

**它粘贴的复现输出会泄露秘密信息吗？**
可能会。技能要求 agent 粘贴调用及其输出，并请求 HAR 文件、日志转储、core dump 等材料。指令并未对这些内容进行净化。[Issue #674](https://github.com/mattpocock/skills/issues/674) 正是提出了这一点（凭据、token、cookie 和个人数据被一并带入聊天、issue 或 PR），并建议增加脱敏约束。该问题仍然开放，尚未实现。目前请将脱敏视为自己的职责，尤其是在任何输出被公开之前。

**我的安全扫描器把这个技能标为高风险。**
Snyk 会标记它，而这个标记是误报。它是技能集中唯一一个附带可执行 shell 脚本（`hitl-loop.template.sh`），同时包含运行脚本及 curl 开发服务器指令的技能。附带 `.sh`、运行指令和出站 HTTP，足以触发静态扫描器。脚本本身大约 30 行，由暂停等待用户输入的 `read -r -p` 提示构成。扫描器评估的是能力范围，而不是已经证明的漏洞。

**`/diagnose` 怎么了？**
在 v1.0.0 中改名为 `/diagnosing-bugs`。旧名称已不存在。你自己的任何调用 `/diagnose` 的内容（封装技能、保存的提示词）都需要更新。

<a id="its-working-if"></a>

## 如何判断它有效

- 提出任何理论之前，先展示命令及其 Red 输出。如果理论先到，说明技能没有真正执行。
- 复现的是你报告的失败，而不是途中发现的相邻问题。
- 开始猜测之前先缩小复现，并能说明剩余每一部分为什么不可或缺。
- 测试任何假设之前，先向你展示已排序的 3–5 个假设，每个都带有可证伪的预测。
- 添加的每条调试日志都带有类似 `[DEBUG-a4f2]` 的标记；宣布完成时，grep 该标记结果为空。
- 提交或 PR 信息说明哪个假设正确。
- 无法用测试锁定 bug 时，直接说明，而不是写一个浅层测试。

<a id="where-it-fits"></a>

## 它在流程中的位置

`diagnosing-bugs` 是随时可用的独立工具。某处坏了就进入，修复和回归测试落地后退出；它不保存状态，也不需要提前设置。[ask-matt](https://aihero.dev/skills-ask-matt) 将 "Something's broken"（某处坏了）路由到这里。

有两个重要的相邻技能。当真正的发现是代码没有合适 seam 来通过测试锁定 bug 时，[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 接收[交接](https://www.aihero.dev/ai-coding-dictionary/handoff)；这项建议会在修复完成、信息更充分之后提出。对于他人提供的原始 bug 报告，[triage](https://aihero.dev/skills-triage) 位于上游，对相同的前两个阶段做较浅的检查。
